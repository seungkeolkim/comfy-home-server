# 결과물 DB metadata: 1차 구현과 2차 검토

상태: **2026-10-15 1차 구현·schema version 10 백필·실제 서비스 적용 완료**. 기존 JSON은 그대로 보존했습니다. 2차 실제 파일 크기·최종 해상도 수집은 사용자 요청으로 보류합니다.

## 개선 전 확인한 구조

2026-10-15에 실행 중인 schema version 9 DB를 읽기 전용으로 확인했습니다.

- `request_results.result_json.output_paths`에는 관리 폴더 기준 상대 경로와 파일명·확장자가 모두 들어 있습니다. 예: `anima/261013_034831_668433672.png`.
- 경로 참조 1,837개는 모두 서로 다른 경로이며, 파일명에서 timestamp와 seed를 읽을 수 있습니다.
- 실제 관리 파일은 2,004개입니다. DB 경로와 일치하는 파일 1,823개 모두 요청 해상도가 있습니다. 실제 파일만 있는 경로는 181개, DB 기록만 있고 실제 파일이 없는 경로는 14개입니다. 불일치 원인은 자동 추정하지 않습니다.
- 요청별 확정 설정은 `result_json.settings`이고, 없는 경우 작업 공통 `job_inputs.input_json.settings`를 사용합니다. 요청 해상도는 실제 최종 해상도와 구분해야 합니다.
- 목록의 mapping SQL은 전체 요청을 탐색하며 `json_each()`로 결과 경로 배열을 펼칩니다. 실제 첫 페이지의 SQL 실행은 약 424~435ms, Python JSON decode는 약 0.19~0.24ms였습니다.
- 앱의 파일 이동은 현재 FS와 해상도 Cache만 갱신하고 DB의 생성 경로는 바꾸지 않습니다.
- 현재 작업 삭제는 생성 당시 경로의 파일만 대상으로 하고 이동된 파일은 보존합니다. 작업 기록만 삭제하면 결과물 파일도 보존합니다.

## 1차: 결과물 전용 테이블과 요청 metadata — 적용 완료

파일당 한 행을 가진 `output_files`를 추가했습니다. 기존 `job_inputs.input_json`·`request_results.result_json`에서 값을 삭제하거나 바꾸지 않고, 목록에서 사용할 값만 추가 column에 백필했습니다. 작업 상세는 기존 JSON을 사용하고 결과물 목록은 직접 조회하는 column과 index를 사용합니다.

추가 column:

| 값 | 목적 |
|---|---|
| `output_id` | 경로 이동과 무관한 결과물 식별 |
| `original_relative_path` | 생성 당시 경로와 기존 삭제 동작 보존 |
| `relative_path` | 현재 파일명까지 포함하는 관리 상대 경로 |
| `request_id`, `job_id` | 작업·요청 필터 및 연결. 이력 없는 파일은 nullable |
| `generated_at`, `seed` | 파일명에서 최초 등록 때 한 번 읽어 정렬 |
| `requested_width`, `requested_height` | 요청 해상도를 직접 조회 |
| `is_available` | 현재 파일 존재 여부. 없는 과거 출력 참조는 이력을 보존하고 목록에서 제외 |

종횡비는 width·height의 최대공약수로 계산합니다. 별도 종횡비 column은 필요하지 않습니다. 파일명·미디어 종류도 저장된 경로 문자열에서 계산할 수 있습니다.

현재 경로의 unique index와 `is_available=1`에 한정한 전체·작업·요청별 정렬 index를 사용합니다. `EXPLAIN QUERY PLAN`에서 전체 목록은 `output_files_listing`, 작업 필터는 `output_files_job_listing`, 요청 필터는 `output_files_request_listing`을 사용하며 임시 정렬이 발생하지 않음을 확인했습니다. `COUNT(*)`는 현재 목록의 총수를 읽는 비용으로 남습니다. Seed는 unsigned 64-bit를 잃지 않도록 decimal TEXT로 보관하고 길이·문자열 순서로 숫자 내림차순 정렬합니다.

일반 목록 요청에서 제거한 작업:

- 결과물→작업 연결을 위한 전체 요청 탐색 및 `json_each()`
- 목록용 전체 `result_json`·`input_json` 읽기와 Python decode
- 작업별 조회의 `get_job()` 상세 JSON 파싱 후 다시 전체 mapping을 조회하는 중복
- 목록마다 전체 FS 탐색·파일 종류 확인·파일명 parsing·Python 전체 정렬
- DB 요청 해상도를 가진 파일의 목록용 이미지 header 읽기

요청 완료 시 기존 결과 JSON 저장과 같은 DB transaction에서 출력 경로·요청 해상도를 등록합니다. 앱의 파일 이동은 현재 경로만 바꾸고 원래 생성 경로와 작업 연결을 유지합니다. 파일 포함 작업 삭제는 삭제·부재 경로를 목록에서 숨깁니다. 이력만 삭제하면 파일과 표시 metadata는 보존하고 FK `ON DELETE SET NULL`로 작업·요청 연결만 해제합니다. 이동된 파일을 파일 포함 삭제에서도 보존하는 기존 정책은 유지합니다.

앱 외부의 파일 추가·이동·삭제는 **서버 시작 또는 결과물 화면의 새로고침 버튼**에서 `scandir()` 목록과 대조합니다. 일반 탭 진입·작업 결과 보기·pagination은 FS 전체 재탐색을 하지 않습니다. 수동 새로고침은 `POST /api/outputs/sync` 후 현재 필터의 첫 페이지를 조회합니다. 외부에서 옮긴 파일은 기존 생성 요청으로 임의 연결하지 않습니다.

### 실제 백필 결과

1. 기존 JSON의 출력 경로·확정 요청 해상도를 한 번 추출합니다.
2. 실제 관리 폴더를 한 번 탐색해 존재하는 경로와 대조합니다.
3. 연결되는 1,823개에는 작업·요청과 요청 해상도를 저장합니다.
4. FS에만 있었던 181개는 이번 개선 전 사용자가 요청한 정리에서 백업 후 삭제됐습니다. 따라서 이번 백필에 포함하지 않았습니다. 이후 외부에서 추가한 파일은 요청·작업·요청 해상도를 임의로 만들지 않고 등록합니다.
5. 실제 파일이 없는 14개의 과거 경로는 현재 목록에서 제외하고 작업 이력의 원래 참조는 보존합니다.
6. timestamp·seed는 경로의 파일명에서 한 번 읽어 저장합니다.

연결되지 않는 이미지의 해상도는 기존 header Cache fallback으로 처리하지만 DB에는 실제 해상도를 쓰지 않습니다. 이번 데이터의 존재하는 1,823개는 모두 요청 해상도가 있어 목록용 header 읽기가 없습니다. 화면은 요청 해상도와 해당 값으로 계산한 종횡비를 표시하고 `(설정)`으로 구분합니다. FS에서 실제 해상도를 읽어 DB에 영구 보관하는 처리는 보류한 2차 범위입니다.

실제 DB 적용 전에 DB 복사본에서 migration을 검증했습니다. 원래 10개 테이블의 모든 행·JSON 문자열 fingerprint가 일치했고 실제 DB 적용 후에도 동일함을 확인했습니다. 작업 203개·요청 2,582개는 보존했습니다. `integrity_check=ok`, `foreign_key_check=[]`입니다.

파일 복사 백업: `runtime/backups/home_server_before_output_catalog_20261015_085014_602.sqlite3`. 일반 schema 9→10 migration에도 기존 백업 helper를 이용한 자동 백업을 남깁니다. 코드만 이전 commit으로 되돌리면 schema 10을 읽을 수 없으므로 복원 시에는 그 코드의 DB 백업도 함께 사용해야 합니다.

비교 결과: 전체 재조회 평균 615.994→46.233ms, 작업 70개 재조회 평균 640.525→43.116ms. 동일한 실제 파일 1,823개·첫 페이지 24개·정렬 순서로 비교했습니다. [단계별 실험 기록](performance_investigation_2026-10-14.md)과 [원시 비교 JSON](performance/output_catalog_2026-10-15.json)에 조건·시간·query plan·백필 검증을 남겼습니다.

## 2차: 실제 파일 metadata 수집 — 보류

후속 schema 변경으로 결과물 행에 nullable `file_size_bytes`, `actual_width`, `actual_height`를 추가하는 안입니다. **생성 완료 시점과 최초 조회 시점 중 어느 때 수집할지는 아직 정하지 않았으며 이번에는 구현하지 않았습니다.** 아래 항목은 생성 완료 시점 수집안의 검토 내용입니다. 요청 하나가 여러 파일을 만들 수 있으므로 metadata는 요청 전체가 아닌 파일별로 저장합니다.

- ComfyUI의 성공한 요청과 실제 Saver 출력 경로를 확인한 뒤 각 파일의 실제 크기·최종 해상도를 수집합니다.
- FS metadata와 이미지 header 읽기는 목록 요청 때가 아닌 완료 시점에 한 번 수행합니다.
- 영상의 실제 해상도는 이미지와 다른 metadata 읽기 방법이 필요합니다.
- 실제 해상도가 있으면 표시와 종횡비 계산에 우선 사용하고, 없으면 요청 해상도를 구분해서 사용합니다.
- metadata 수집 실패가 이미지·영상 생성 성공을 실패로 바꾸지 않도록 합니다. 미수집 값을 구분하고 나중에 보완할 수 있어야 합니다.

기존 파일은 일회성 FS 백필이 필요할 수 있습니다. FS 읽기는 긴 DB 쓰기 transaction 밖에서 수행하고 결과를 묶어 반영하는 방식을 검토합니다.

2차의 주된 이점은 최종 해상도의 정확성, 재시작 후에도 유지되는 metadata, 목록 요청에서의 header 읽기 제거입니다. 1차에서 요청 해상도로 처리되는 파일은 반복 조회의 추가 속도 개선폭이 작을 수 있습니다. MiniMax는 해상도 정렬·upscale 때문에 요청 해상도와 최종 해상도가 달라질 수 있어 실제 값 보관의 의미가 큽니다.

## 남는 처리와 검증 기준

- 실제 파일·영상 전송, 최초 Thumbnail 생성에는 파일 내용 읽기가 필요합니다.
- 썸네일의 현재 key는 경로·수정 시각·크기이므로 이 두 단계만으로 모든 썸네일 `stat()`이 없어지지는 않습니다. 별도 Cache 정책 검토 대상입니다.
- 코드에 남는 작업 상세·Prompt JSON 파싱은 목록과 분리해 유지할 수 있습니다.
- 외부 FS 변경은 서버 시작·수동 새로고침에서 대조합니다. 생성 성공 후 DB 기록이 없는 파일도 이때 연결 없는 결과물로 등록할 수 있습니다.
- 1차·2차는 별도 migration 및 백필로 진행하고, schema 변경 직전에 백업 상태를 확인합니다.
- 목록 수·정렬·pagination·작업/요청 필터·이동·이력만 삭제·파일 포함 삭제를 검증합니다.
- 서버 재시작 직후와 Cache 재사용 조건을 구분해 같은 데이터로 HTTP와 단계별 시간을 비교합니다. 예상 시간을 측정 결과로 단정하지 않습니다.

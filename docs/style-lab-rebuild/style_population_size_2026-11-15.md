조사 당시 원본은 활성·평가 22개, 부모 6개였고 저장된 생성 수량은 Random 1개·진화 6개였습니다. 위 50·12개는 설치본의 Factory 기본값이며 당시 저장값과 다릅니다. CHS 주 프로젝트는 활성 10개·퇴역 25개·취소 7개였습니다.

원본의 북마크 보호 때문에 활성 수가 늘어날 수 있지만 CHS에는 해당 기능이 아직 없습니다. 이를 이유로 모든 자녀를 자동 생존시키거나 퇴역 후보를 되살리지 않습니다. Mutate/Crossover/Random의 1:1:1 추첨과 부모 Selection·Elo·Undo 정책도 유지합니다.

## 반영한 사용 흐름

- 새 Random 기본값 50개·상한 1000개, 진화 기본값 12개·상한 60개를 서버와 Web에 적용합니다. 사용자가 더 작거나 크게 지정할 수 있습니다.
- 생성 화면에 활성 조합 수·부모 수를 짧게 표시합니다. 활성 1~49개에서는 **50개까지 늘리기 (+부족분)** 버튼을 제공합니다. 활성 10개면 입력값만 40으로 바뀌며, 별도의 생성 버튼과 기존 확인창을 거쳐야 실제 생성됩니다. 50개는 확장용 기준이며 최대 활성 수가 아닙니다.
- 추가한 조합을 선별해 50개 모두 평가되면 다음 진화 부모는 15개입니다. 기존 10개와 Elo·이미지는 유지하고 신규 조합을 같은 평가 조건에 추가합니다. 다중 Prompt 이미지 수는 조합 수 × Prompt 수입니다.
- 마지막 제출한 Random·진화 수량은 프로젝트별로 기억합니다. 새 Browser나 서버 재기동 뒤에도 기존 불변 계획·소유 Job 기록에서 복원하므로 새 테이블·Schema 변경·프로젝트 Revision 변경이 없습니다. 준비 후 확인을 취소한 계획은 마지막 제출 수량을 바꾸지 않습니다.
- 새 정책 표시 `stylelab-generation-counts-v1`가 있는 제출 계획부터 수량을 복원합니다. 과거 작은 기본값이 첫 적용 시 새 50·12개 기본값을 덮어쓰지 않게 하며, 기존 계획 JSON을 소급 수정하지 않습니다. 현재 Browser에 남은 미제출 계획은 그대로 재확인할 수 있습니다.
- Prompt 변경 후 같은 조합 재생성도 최대 1000개를 처리해 50개 Pool이 종전 32개 제한에 잘리지 않게 합니다. 26개를 넘는 내부 조합 Label은 A..Z, AA..AZ, BA.. 순서로 만듭니다. 사용자 표시·파일 이름은 기존 세대·조합 번호 규칙입니다.
- 새 생성 제출 시 이전 선별 Cache와 진행 중 조회를 무효화합니다. 새 자녀가 준비되기 전에 이전 Pair의 버튼이 잠깐 활성화되던 문제를 함께 수정하며, 접수 응답 유실 때도 서버에서 최신 대결을 다시 읽습니다.

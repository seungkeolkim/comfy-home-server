## 한 번의 작업을 진행하는 규칙

1. 시작할 때 이번 단계에서 가능한 행동, 만드는 화면, 아직 만들지 않을 범위, 확인 방법을 짧게 알립니다. 이전 확인 내용을 이미 받았다면 같은 내용을 다시 묻지 않습니다.
2. 해당 단계만 구현하고 필요한 테스트와 Browser 검증을 먼저 수행합니다. 사용자가 처음 버그를 발견해야 검토할 수 있는 상태로 넘기지 않습니다.
3. 사용자에게 접속 위치, 눌러볼 순서, 확인할 질문 2~3개, 알려진 제한을 전달합니다. 목업·실 데이터·실제 이미지 생성 여부를 구분합니다.
4. **사용자가 직접 확인한 뒤 다음 단계 진행을 요청할 때까지 기능 범위를 확장하지 않습니다.** 응답이 없거나 자동 테스트가 통과했다는 이유로 다음 단계를 시작하지 않습니다.
5. 수정 요청은 같은 단계에서 반영합니다. 화면이나 기본 흐름이 달라지면 다시 직접 확인할 수 있게 전달합니다.

기본적으로 `다음 단계 진행`은 바로 다음 한 단계를 뜻합니다. 여러 단계를 묶으려면 사용자가 그 범위를 명시합니다. 큰 단계의 중간 확인점도 아래에 따로 표시했습니다.

함수 구현·일반적인 오류 수정·테스트 실행마다 확인을 요구하지 않습니다. 사용자는 사용 방식과 결과를 판단하고, 개발자는 데이터 격리·동시성·재현성 등 기술 검증을 책임집니다. 기존에 허용한 서버 재시작도 필요한 범위에서 진행하되, 재시작 후 실제 접속 상태를 확인해 보고합니다.

## 단계별 범위와 통과 기준

### 0. 구현 전에 가장 짧은 사용 흐름부터 확인

우선 `프로젝트 선택·생성 → 조합 생성 → 이미지 비교 → 마음에 드는 조합 확인`만 연결한 Desktop·Mobile 화면안을 보여드립니다. 전체 9개 화면과 고급 설정을 한꺼번에 만들지 않습니다. 필요한 경우 작은 클릭 목업으로 확인하되 예시 데이터임을 표시합니다.

현재 8389 Web·Mobile에서 유지할 조작을 먼저 확인합니다. 비교 화면에는 같은 A/B의 여러 Prompt 결과·Mobile Case 전환과 STR 차이·제외 진입점을 포함합니다. 조합 단위로 한 번 선택하며 Prompt별 투표 토글은 없습니다. 융합 UI 전체는 해당 후순위 차례까지 미룹니다.

처음 정할 것은 첫 화면, 프로젝트 생성에 반드시 필요한 입력, 비교 화면에 항상 보일 정보, 다음 행동의 위치입니다. Workflow·Prompt·성분 범위 등 입력을 어디에 두는지 실제 예시로 확인합니다. 내부 용어인 Evaluation Revision·RenderPlan을 일반 조작에 그대로 노출하지 않습니다.

**사용자 확인:** 설명 없이 프로젝트를 시작할 위치를 찾을 수 있는지, 비교 화면에서 이미지가 충분히 큰지, 설정 때문에 탐색이 끊기지 않는지 봅니다. 사용자가 선택한 흐름을 기록한 뒤 1단계를 시작합니다. 지금 문서 작성만으로 이 선택이 완료됐다고 기록하지 않습니다.

### 1. Fresh 프로젝트 하나를 만들고 다시 열기

[22번 작업·출력 분리 결정](22_style_job_output_separation_and_project_rename.md)을 저장 경계에 반영합니다. 프로젝트 이름과 안정적인 소유 ID를 분리하고 자동 작업분류·출력 위치 및 Rename Operation을 연결할 수 있게 합니다. 웹에서 이름을 바꾸면 출력 폴더·분류명도 따라 바뀌어야 하며, 작업 메모는 이름 변경의 영향을 받지 않도록 세대부터 작성합니다.

프로젝트 이름·목적, 등록 Workflow, Prompt/Negative, 지원되는 생성 조건을 저장하고 조회합니다. 프로젝트 생성만으로 GPU 작업을 제출하지 않습니다. 처음에는 Fresh만 연결하며 점수 이전·분기는 각 단계에서 붙입니다.

Prompt Set은 처음 필요한 저장 구조에 포함합니다. 2개 이상 Case를 저장·다시 열 수 있고, 한 Prompt 사용도 가능합니다. Case 구성·내용·평가 정책의 불변 Version 경계를 정의합니다.

설정 항목은 등록 Adapter가 실제 지원하는 범위로 제공합니다. 모델·Sampler 등 아직 제어하지 못하는 항목을 동작하는 것처럼 노출하지 않습니다. 생성 조건의 저장 구조와 최소 필요한 Migration 범위를 함께 검토합니다.

**개발자 검증:** 프로젝트 A/B의 조건 격리, 재접속·재시작 후 복구, 일반 생성과의 입력 상태 보존. 이후 평가와 복원의 경계를 저장할 수 있도록 Project·평가 조건 Snapshot의 소유 관계를 정합니다.

**사용자 확인:** 서로 다른 Prompt의 프로젝트 두 개를 만들고 오가면서 설정 위치와 저장 결과를 확인합니다. 다음 행동이 불분명하면 이 단계에서 화면을 줄이거나 바꿉니다.

### 2. 평소 Workflow와 같은 실제 결과가 나오는지 먼저 확인

[22번](22_style_job_output_separation_and_project_rename.md)의 모델/프로젝트 자동 작업분류, `세대003-01 이미지 생성` 메모, 전용 출력 루트와 일반 작업·이미지 탭의 기본 숨김 Checkbox를 연결합니다. 기존 Workflow 출력 형식을 유지하며 스타일 구성 Job·출력의 임의 이동을 UI/API에서 막습니다. 실제 파일이 생긴 뒤 프로젝트 이름 변경 시 폴더·분류·조회 참조의 일관성과 중단 복구도 검증합니다.

알려진 고정 조합 두 개로 작은 실제 생성 검증을 합니다. 이 검증을 위해 수동 조합 편집 도구 전체를 만들지는 않습니다. 공통 Prompt 전개·Sampling Seed·설정을 고정하고 Home의 등록 Workflow/Adapter 경로를 사용합니다.

먼저 한 Case로 Workflow를 대조한 뒤 2개 이상 Case로 확장해 같은 조합을 생성합니다. 후보 2개×Prompt 2개×Seed 1개는 재사용이 없으면 4장입니다. 이 차례에 장수와 모든 Case의 Render 소속·부분 실패 재시도를 확인합니다.

**개발자 검증:** 제출 직전 Graph, 실제 Encode 입력, Seed, LoRA Model/CLIP Strength와 0 값, Trigger 정책, NegPip 연결, Output 등록, PNG Metadata를 대조합니다. 허용한 동적 Field 외 Workflow 차이를 확인합니다. 동일 조건·Runtime의 반복 재현을 확인하되 Seed만으로 모든 환경에서 같은 픽셀을 보장한다고 안내하지 않습니다.

성공·실패·완료 여부 미확인을 구분하고 Browser 종료 후에도 추적합니다. 예상된 Model Only의 TE 미사용은 상세 적용 기록으로, 실제 Model/Patch 문제는 오류로 표시합니다. 프로젝트 소유 작업의 취소가 일반 생성까지 중단하지 않는지도 확인합니다.

**사용자 확인:** 평소 쓰는 Prompt와 대표 LoRA로 결과·설정을 확인합니다. Workflow 일치에 의문이 남으면 Random 생성이나 진화를 추가하기 전에 해결합니다. 화면 품질 판단과 실제 Graph·Log의 적용 검증은 별도로 기록합니다.

### 3. 초기 조합 생성과 잠금

현재는 작은 단위로 나누어 **3A Random 초기 조합·장수 확인·생성**을 먼저 구현합니다. [3A 검토 문서](phase_three_review.md)에서 확인합니다. 이후 사용자 요청으로 **3B 공통 성분 잠금보다 4A 선별·Elo·Undo를 우선**하도록 순서를 바꿨습니다. 아래 잠금까지 포함한 검증 항목은 3단계 전체 목표이며 3A 완료 항목으로 표시하지 않습니다.

작가·LoRA 후보군, 사용할 개수·Weight 범위, 작가만/LoRA만 사용을 설정하고 작은 Batch부터 생성합니다. 프로젝트 공통의 성분 유지·선택 Weight 축 고정을 이때 연결합니다. 먼저 UI에서 규칙과 예정 장수를 확인할 수 있게 합니다.

**개발자 검증:** 중복 방지, 유한 재시도, 잠금 충돌 사전 거부, 부족 후보 수 표시, 독립 Model/CLIP Strength 보존. 공통 잠금 검증을 이후 Mutate/Crossover에도 재사용하며 기존 후보를 소급 수정하지 않습니다.

**사용자 확인:** 예를 들어 네 조합을 만들어 어떤 부분이 달라졌는지 확인합니다. 네 개는 조작 확인용이며 진화 최소 평가 수를 낮추는 정책 변경이 아닙니다. 필요한 경우 이후 명시적 추가 생성으로 진화 조건을 채웁니다.

### 4A. 비교·순위와 성분 차이·향후 사용 제외

사용자의 우선순위 변경에 따라 3B 잠금 전에 이 단위부터 연결합니다. 실제 구현 범위와 확인 순서는 [4단계 검토 문서](phase_four_review.md)를 기준으로 합니다.

A/B, 비슷함, Undo, Blind, 확대, Mobile 나란히/한 장씩을 연결합니다. 현재 조합과 순위를 확인할 수 있게 합니다. 비교 도중 점수·태그가 판단을 방해하는지, 투표 후 다음 Pair가 자연스럽게 보이는지를 우선 확인합니다.

작가·LoRA를 긴 한 줄 대신 A에만/B에만/강도 변경/동일로 대조하고 Model/CLIP 축·순서·파일 차이를 구분합니다. 성분 행에서 현재 프로젝트의 향후 새 조합 사용 제외·재허용을 제공합니다. 기존 후보·점수 보존, 잠금 충돌과 Blind에서의 이름 숨김, 세 생성 방식의 상속 제어를 검증합니다. 차이를 확정적인 원인으로 표시하지 않습니다.

**개발자 검증:** 일반 Elo의 10000 대 10000 승리 결과 10160/9840, Match Kind별 Skip 의미, Placement, 중복 Vote·오래된 Token 거부, 영속 Event·Undo, 이미지 준비 전 투표 금지, A/B 위치와 의미 일치. 기존 알고리즘 Fixture를 기준으로 하며 모든 비교를 일반 Elo로 단순화하지 않습니다.

**사용자 확인:** 여러 번 선택하고 비슷함·Undo를 실행한 뒤 프로젝트와 기기를 바꿔 다시 열어봅니다. 비교가 번거로우면 진화 버튼을 추가하기 전에 고칩니다. 설명만으로 확인한 상태와 실제 사용한 상태를 구분합니다.

### 4B. 여러 Prompt 결과를 함께 보고 판단

같은 A/B를 여러 Case에서 보여주는 Desktop Matrix와 Mobile Case 전환을 실제 이미지로 확인합니다. 단일 Prompt 비교는 조작 확인용 중간 상태이며 이 단계까지 완료됐다는 뜻이 아닙니다.

**개발자 검증:** 같은 Case·Seed의 대응, A/B 위치 유지, 필수 결과 준비·실패 표시, 중복 Vote 방지. 조합 단위 한 표와 Match·Elo·Skip·Undo·성분 관측 수를 맞춥니다. 이전 평가 구간이나 최종 검증의 점수를 임의로 합치지 않습니다.

**사용자 확인:** Prompt마다 장단점이 갈려도 전체 결과에서 조합 하나를 판단하기 쉬운지 확인합니다. 같은 선택을 진화 부모 선정에 연결하며, 준비되지 않은 Case를 빼고 몰래 평가하지 않습니다.

### 5. 얻은 스타일을 보관하고 실제로 다시 쓰기

둘 이상의 스타일에 이름·Memo를 붙여 보관하고 성분·Weight·조건·이미지를 다시 엽니다. 보관은 불변 Snapshot이며 북마크의 진화 정리 보호와 구분합니다. 기존 후보 수정으로 보관 내용이 바뀌지 않아야 합니다.

`일반 생성에 가져오기`는 사용자가 명시적으로 실행합니다. 적용할 항목과 Workflow 호환성 차이를 보여주고, 일반 생성에 작성하던 입력을 무심코 덮어쓰지 않습니다. 공간 전환 자체는 적용이나 생성을 실행하지 않습니다.

**사용자 확인:** 스타일 두 개를 보관하고 나중에 찾아 하나를 일반 생성에 적용합니다. 이 흐름이 편해야 기본 사용 구간을 통과한 것으로 봅니다.

### 6. 성분 점수와 점수만 이어받기

현재 후보에 근거한 성분 점수와 가져온 Prior를 구분합니다. 새 프로젝트 생성에 `점수만 이어받기`를 추가하고 출처·근거 수·새 관측 수를 보여줍니다. 이 단계는 전체 Legacy 이관과 분리합니다.

13번 자료에는 작가 197개와 LoRA 10개의 Snapshot이 있습니다. **작가 점수는 모두 0이고 LoRA 점수에는 관측값이 있습니다.** 이전 기록이 있다는 이유로 모든 작가에게 유효한 선호 점수가 있다고 표현하지 않습니다. 이 자료는 조사 당시 Snapshot이며 최신 운영 데이터인지는 별도 확인합니다.

**개발자 검증:** Fresh의 Ridge 산식 일치, 관측 0에서 Prior 보존, 원본 변경 비전파, 새 후보·Vote·승패 0과 세대 1, 서로 다른 모델/Prompt의 차이와 호환성 처리. LoRA 점수를 추출 확률에 쓰는 새 정책은 기존과 달라지는 부분이므로 정책값을 기록하고 확인합니다.

**사용자 확인:** Fresh와 점수 이전 프로젝트를 나란히 열어 무엇이 유지되고 초기화됐는지 확인합니다. 점수 상세 정보는 필요할 때 펼치도록 구성합니다.

### 7A. 다음 세대 계획을 먼저 확인

실제 진화 제출 전에 부모·계보 대표·계보별 자녀 수·잠금·Mutate/Crossover/Random 배정을 보여줍니다. 계보별 기회, 다른 계보 사이의 Crossover 허용, 예산 부족 처리 등 문서에서 미확정인 정책값은 이 시점에 구체적인 예로 확인합니다.

4B에서 확인한 여러 Prompt 평가 정책이 부모 순위에 어떻게 반영되는지 함께 보여줍니다. 장수는 자녀 수×Case 수×Seed 수를 기준으로 계산하고, 제외한 성분이 상속으로 재등장하지 않는지 확인합니다.

**개발자 검증:** 기존 상위 30%와 최소 평가 조건, 대표 계보의 부모 기회, 공통/계보 잠금 충돌, 고정 부모 점수와 정책 Version, 재현 가능한 배정 근거. 북마크와 계보 대표의 의미를 구분합니다.

**사용자 확인:** 부모와 변경 범위가 의도에 맞는지 확인합니다. 계획 화면을 사용자가 확인하기 전에는 이 단계의 다음 세대 생성을 자동 실행하지 않습니다. 기존 세대 확정 시점의 Checkpoint를 저장할 준비도 이때 마칩니다.

### 7B. 한 세대만 생성·선별·확정

확인한 계획으로 자녀를 만들고 기존 Selection 계약으로 평가합니다. 살아남을 자녀와 퇴역할 후보를 확인한 뒤 한 세대를 확정합니다. 취소와 실패 재시도도 같은 단위에서 처리합니다.

**개발자 검증:** 부모 점수 고정, Batch별 Vote 범위, 자녀 배치, 북마크 보호, 활성/퇴역 처리, 계보 배정·잠금 보존, 취소, 재시작 후 상태. **최초 세대와 이후 각 확정 시점부터** 복원에 필요한 상태·Event 경계·Asset Manifest를 일관되게 저장합니다. 복원 기능을 붙일 때 과거 상태를 추측하지 않습니다.

**사용자 확인:** 생성된 방향, 필요한 비교량, 확정 전후 변화와 세대 번호를 직접 확인합니다. 불편하면 같은 단계에서 조작을 수정합니다. 반복 실사용과 많은 세대 축적에 앞서 8단계를 검증합니다.

### 8. 세대 복원은 테스트 데이터로 직접 확인

테스트 프로젝트에서 두 확정 시점과 이후 Vote·보관 변경을 만든 뒤 이전 Checkpoint로 돌아갑니다. 처음에는 취소를, 다음에는 실제 복원을 실행해 봅니다.

**사용자 확인:** 경고창 한 번에 프로젝트·평가 조건·목표 세대, 이후 이미지·이력·승패·Elo 변경·보관 결과 삭제와 실제 수량이 이해되는지 확인합니다. 점수는 0이 아니라 선택 시점의 값으로 돌아가야 합니다.

**개발자 검증:** 이전 세대 후보에 가한 이후 Vote까지 복원, 중복 요청·오래된 Token·늦은 Callback 거부, 다른 프로젝트와 공유 Asset 보존, 파일 정리 실패·재시작 복구. 기능이 추가될 때마다 종속 Trial·실험과 독립 분기의 삭제 경계 테스트를 함께 보강합니다.

### 9A. Prompt를 바꾸고 같은 조합으로 생성

현재 순위 상위 N개의 실제 대상과 성분·Weight를 고정하고 새 Prompt로 생성합니다. 먼저 N=1~2로 생성 결과와 원본/신규 보기를 확인합니다. 원본 조건·Seed가 달랐다면 차이를 표시합니다.

**개발자 검증:** 성분·순서·모든 Strength 보존, Random/Mutate/Crossover 미호출, 공통 Prompt 전개, 세대 불변, 원본 이미지·통계 보존. 재시험에는 최신 잠금을 소급 적용하지 않습니다.

**사용자 확인:** 기존에 원하셨던 “다음 세대를 만들지 않고 새 Prompt를 시험”하는 행동이 맞는지 확인합니다. 이 단계에서 결과가 다르면 채택 기능을 붙이기 전에 원인을 해결합니다.

### 9B. 시험 안에서 비교·제외·채택

시험 내부 Elo 10000/전적 0에서 비교하고 Drop·Drop 취소·Undo를 제공합니다. 시험 보관, 시험 폐기, 성공한 미제외 후보와 새 Prompt 채택을 구분합니다.

**개발자 검증:** Drop을 패배로 기록하지 않기, 원본 Elo 미혼합, 실패 항목만 재시도, 오래된 채택 Token 거부, 채택 전 종속 Trial/채택 후 독립 평가 구간의 복원 경계. 출발 세대 N을 유지하고 실제 다음 진화는 N+1입니다. 남은 평가 후보가 진화 조건에 부족하면 이유를 알립니다.

**사용자 확인:** 한 후보를 Drop했다가 복구하고 Trial을 채택합니다. 현재 보고 있는 순위가 원본인지 시험인지, 채택 후 남은 조합과 다음 행동이 분명해야 통과합니다.

### 10. 탐색 방향을 독립 프로젝트로 분기

안정된 현재 상태 또는 확정 세대에서 같은 조건의 새 프로젝트를 만듭니다. Prompt/모델 변경과 옛 Elo 이전을 한 동작으로 묶지 않습니다. 조건 변경은 분기 후 재시험 또는 새 평가로 처리합니다.

**개발자 검증:** 새 소유 ID, 출발 N/다음 N+1, 가져온 통계와 새 관측 구분, 원본 Vote를 새 Vote로 재생하지 않기, 분기 후 Vote만 Undo, 공유 이미지 참조 보호. 원본 복원·삭제가 분기 데이터에 영향을 주지 않아야 합니다.

**사용자 확인:** 원본과 분기에서 다른 선택을 하고 한쪽을 복원해 독립성을 확인합니다. 여기까지 통과한 뒤 10번 문서의 P0 수락 기준을 다시 대조해 MVP 완료 여부를 판단합니다.

## Browser 검증과 사용자 확인의 역할

Browser 자동화는 동작·배치 오류를 찾는 수단입니다. 사용자 의도와 사용성의 통과 여부를 대신 판단하지 않습니다.

| 개발자가 전달 전에 확인 | 사용자가 직접 판단 |
| --- | --- |
| Desktop·Mobile·좁은 폭에서 버튼/확인창 잘림, 입력·Scroll 상태 유지 | 원하는 작업을 어디서 시작할지 바로 알 수 있는가 |
| 두 이미지 준비, Vote 연타, 실패·진행·빈 상태 | 이미지 크기와 비교 동작이 편한가 |
| Graph·Seed·성분·Metadata·DB와 화면의 일치 | 평소 Workflow로 얻으려는 탐색 결과인가 |
| 재시작·중복 요청·프로젝트 격리·복원 범위 | 설정과 설명이 많아 작업을 방해하지 않는가 |

단계 인계에는 다음 형식을 사용합니다.

```text
현재 단계: 4 — 비교와 순위
가능해진 행동: A/B 선택, 비슷함, Undo, Blind, 현재 조합 확인
접속 위치: 실제 URL과 프로젝트 이름
확인 순서: 비교 세 번 → 비슷함 → Undo → Mobile 한 장씩 보기
개발자 검증: 통과한 검사와 실제 생성/API 연결 여부
사용자 확인점: 이미지 크기 / 버튼 위치 / 다음 Pair 전환
남은 제한: 이번 단계에서 제공하지 않는 기능
다음 단계: 직접 확인 후 요청하시면 5단계 진행
```

각 단계는 **구현됨 / 개발자 검증됨 / 사용자 확인됨**을 구분해 기록합니다. 테스트 통과만으로 `사용자 확인됨`이나 `사용 가능 확정`으로 표시하지 않습니다.

## 되돌릴 수 있는 작업 크기와 기록

시작할 때 Branch·기준 Commit·변경 파일·실제 DB Schema를 확인합니다. 작은 변경에는 해당 단계의 테스트를 수행하고, 의미 있는 데이터·동시성 변경에는 관련 수락 검증을 추가합니다. 모든 미래 기능의 테이블과 빈 화면을 미리 만들지 않습니다. 다만 이미 생성한 데이터의 소유·평가 조건·복원 근거는 처음 필요한 단계부터 기록합니다.

DB Migration이 필요한 단계에서는 적용 전 일관된 Backup의 경로·시각·Schema를 기록하고 임시 사본에서 적용·복구를 확인합니다. 운영 DB는 일반 생성 이력도 공유하므로 **기능 코드 수정이나 UI 불만이 있을 때 DB 전체를 자동 복원하지 않습니다.** 되돌릴 코드·DB·파일 범위를 먼저 구분하고 해당 사용자 지시에 맞춥니다.

검토용 프로젝트·생성물은 식별 가능하게 기록합니다. 사용자의 기존 Style Lab, 등록 Workflow 원본, 모델·LoRA 파일과 무관한 데이터를 임의 정리하지 않습니다. 진행 기록에 비밀번호·Cookie를 남기지 않습니다.

사용자가 Commit을 요청하면 확인 범위를 작게 묶어 Commit합니다. Push는 별도 지시를 따릅니다. 화면·기본값·사용 흐름 결정은 관련 요구사항 문서와 이 파일의 진행 기록에 반영하고 원문 Snapshot은 보존합니다.

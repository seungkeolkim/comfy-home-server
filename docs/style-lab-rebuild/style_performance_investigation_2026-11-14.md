# 스타일 구성의 첫 탭 진입·다음 대결 지연 조사

2026-11-14. 기준 Commit `d63ead2`. 운영 CHS 8388·StyleLab 8389를 읽기 전용으로 조사했습니다. 운영 코드는 변경하지 않았습니다.

결론은 **썸네일 Cache 용량보다 중복 Polling, 투표 후 불필요한 전체 조회, 반복 DB·파일 검사가 주요 병목**이라는 것입니다. 현재 일반 생성의 Summary·상세 분리, Output Catalog, 중복 요청 병합 방식을 가져올 수 있습니다.

## 측정 조건

- 같은 PC의 localhost에서 Edge Headless를 사용했습니다. 390px·1280px Viewport는 각각 모바일·데스크톱 배치이며 실제 휴대전화나 외부망 속도 측정은 아닙니다.
- 큰 프로젝트에는 조합 42개가 있으며, 선별 활성 조합 16개와 조합당 Prompt 3개를 검사합니다. 다른 작은 프로젝트에는 조합 2개가 있습니다. 생성 요청 결과 JSON은 전체 109건·약 18.4MB입니다.
- 운영의 첫 화면·GET API는 실제 서비스로 측정했습니다. 운영 로그인 외 POST·생성·투표·삭제를 실행하지 않았습니다. 두 서비스의 보관 이미지 수·구성은 다르므로 동일 데이터의 완전한 A/B 비교는 아닙니다.
- 투표 시간은 운영 DB의 복사본과 같은 Docker Image·소스·Windows Bind Mount로 만든 격리 서버 18388에서 측정했습니다. 이미지 Mount는 읽기 전용이고 Warmup은 껐습니다. 운영 8388은 재기동하지 않았습니다.
- 투표 실험은 매번 Undo로 같은 시작 상태를 복원했습니다. 정기 Polling은 두 비교군 모두 멈추고, 기존 투표 처리와 응답 재사용 처리만 비교했습니다. 실제 운영은 Polling 중첩으로 더 느릴 수 있습니다.
- 원본 StyleLab에서도 170ms 선택 강조와 1000ms 결과 공개가 동일하게 적용됩니다. 이번 비교에서는 두 시간을 줄이지 않았습니다.

## 지연 원인

1. **2초 Polling이 이전 조회 완료를 기다리지 않습니다.** `scheduleStyleGenerationRefresh()`는 `refreshStyleGenerationResults()`의 Promise를 기다리지 않고 2초 Timer를 시작합니다. 조회는 결과→선별→진화 순으로 약 2.33초가 걸립니다. 이전 조회가 끝나기 전에 `resultRefreshSequence`가 증가해 DOM 갱신이 계속 취소됩니다. 데이터 42개는 Browser 상태에 들어왔지만 화면은 `아직 생성한 이미지가 없습니다`에 머물렀습니다.
2. **투표 응답의 다음 대결을 바로 그리지 않습니다.** `/votes` 응답에는 이미 다음 Match와 Elo가 있습니다. 현재 코드는 결과 공개 후 `generation-results`→`selection`→`evolution`을 다시 기다리고 화면을 그립니다. StyleLab은 같은 공개 시간 뒤 응답의 Match를 바로 그립니다.
3. **결과 목록에서 전체 생성 조건과 Graph를 반복해서 읽습니다.** 한 번의 `results()` 호출은 SQL `execute` 190회, `fetchall` 51회, JSON Decode 208회입니다. 프로파일에서 DB 실행·읽기가 약 1.05초, JSON Decode가 약 0.12초였습니다. 카드에 필요 없는 `prepared_graph`·`metadata_workflow` 등을 포함한 원본 요청 JSON을 읽고 대부분 버립니다.
4. **화면 조회마다 모든 활성 이미지의 경로·존재를 검사합니다.** 선별 조회 한 번에 `managed_path` 48회, `lstat` 528회, `stat` 240회가 발생했습니다. 경로 검증 약 385ms와 `is_file` 약 60ms가 약 494ms 조회의 대부분입니다. 진화 조회도 같은 검사를 다시 수행합니다.
5. **Windows Bind Mount가 반복 I/O 비용을 키웁니다.** 같은 소스와 복사 DB의 Windows Native 프로파일은 결과 203ms·선별 23ms·진화 37ms였습니다. Docker에서는 각각 1,238ms·494ms·595ms였습니다. 이 실험은 반복 I/O의 비용을 확인하기 위한 것이며 배포 구조 변경이 필수라는 결론은 아닙니다.
6. **추가 Index만으로는 충분하지 않습니다.** 일반 목록의 `output_files_request_listing`은 가용/미삭제 조건의 Partial Index인데 스타일의 파일별 조회에는 그 조건이 없어 Table Scan이 발생합니다. `style_candidate_renders(candidate_id)` 조회도 Scan입니다. 복사 DB에 일반 Index 두 개를 추가한 결과 조회는 약 1.24초→1.14초였습니다. 주요 개선은 조회 횟수·읽는 본문 축소와 함께 해야 합니다.

관측한 운영 Thumbnail Preview 11건의 중앙값은 약 35ms였습니다. 격리 서버의 첫 새 이미지 Preview는 약 86~146ms였습니다. 기존 Thumbnail Cache는 이미 공유하고 있습니다. 기동 Warmup은 현재 일반 출력 루트만 순회하므로 스타일 첫 접근에 Cache Miss가 날 수 있으나, 15초 미표시나 투표 후 약 2.4초 추가 대기의 주원인은 아닙니다.

## 재사용할 구현과 권장 순서

1. **Polling 중복 방지부터 적용합니다.** 일반 생성의 `loadPromise`, `jobsReloadRequested`, Revision 검사처럼 같은 프로젝트의 실행 중 조회는 합치고, 완료 후 다음 Timer를 시작합니다. 화면 이동·삭제·프로젝트 전환에 대한 오래된 응답 차단은 유지합니다. 첫 결과를 표시하는 데 진화 부가 정보까지 기다리지 않게 합니다.
2. **투표 응답을 화면에 바로 적용합니다.** 같은 조합의 이미지·성분·Prompt는 Browser에 이미 있으므로 응답 Match·Elo만 갱신합니다. 진화 진행 표시는 뒤에서 갱신하고 결과 공개 중 다음 Pair의 이미지를 미리 요청·Decode합니다. 공개 시간은 유지할 수 있습니다.
3. **일반 작업의 Summary·상세 분리를 가져옵니다.** `refreshJobPages()`는 `summary=true` 목록을 읽고 `loadJobDetails()`는 펼친 작업만 상세를 읽으며 동일 요청을 합칩니다. 스타일도 카드·선별에는 ID·성분·Elo·Thumbnail·Seed·상태만, 실제 Prompt·Graph·생성 상세는 열 때 조회합니다.
4. **Output Catalog를 목록·준비 상태 조회에 사용합니다.** 일반 결과물은 `output_files`의 가용/미삭제·경로·해상도·정렬·페이지 정보로 표시합니다. 스타일도 Render와 Catalog를 일괄 Join하고 Partial Index 조건을 맞춥니다. 실제 파일·symlink 검사는 미디어 접근, 실제 투표 대상, 생성/확정/삭제 같은 동작 경계에 유지합니다. 외부 파일 삭제 후의 동기화 정책도 함께 검증해야 합니다.
5. **화면별 필요한 범위만 읽습니다.** 선별은 현재 Pair·다음 Pair, 그림체는 현재 페이지·필터만 읽고, 생성·진화 이력은 해당 탭에서 읽습니다. 일반 결과물 목록의 페이지 조회와 상태 변화가 있을 때만 상세 Cache를 무효화하는 방식을 재사용할 수 있습니다.
6. **이미지 변경이 없는 DOM은 유지합니다.** StyleLab의 keyed `morph`는 공개 중 같은 이미지 노드를 보존합니다. CHS는 `innerHTML`로 넓은 영역을 여러 번 교체합니다. 일반 CHS의 열린 Viewer 소스를 유지하는 개념과 함께, 제목·Elo·선택 강조만 갱신하도록 가져올 수 있습니다.

우선 1·2를 작은 변경으로 처리한 뒤, 같은 데이터로 다시 측정하고 3·4를 적용하는 순서가 적절합니다. 5·6과 스타일 Warmup 확장은 후순위입니다. Cache 개수 확대보다 불필요한 작업을 줄이는 쪽의 효과가 직접 확인됐습니다.

## 원본 보존과 산출물

# Web UX 기준·비율 융합·여러 Prompt 탐색·성분 차이 보기

작성일: 2026-11-10, Asia/Seoul. 0단계 시작 전 전달받은 요구사항을 반영합니다. 이 문서는 요구사항과 설계 후보를 기록하며 실제 UI·생성·DB 구현은 포함하지 않습니다.

## UX 기준과 결정 상태

사용 경험의 기준은 **현재 `http://localhost:8389`에서 사용 중인 Style Lab Web을 Desktop·Mobile Browser로 이용하는 흐름**입니다. 이 문서의 현재 사용 경험은 사용자 설명을 기준으로 합니다. 서버 상태나 화면을 이번 문서 작업에서 새로 검증한 것은 아닙니다.

기존 Web의 편리한 흐름을 출발점으로 삼고, 프로젝트·Workflow 일치와 아래 개선을 더합니다. 18번의 정적 목업은 비교·수정할 화면안이며 사용자가 확인한 최종 UX로 간주하지 않습니다. 0단계에서 익숙한 Web의 어떤 조작을 유지할지도 함께 확인합니다.

| 항목 | 사용자 요구·방향 | 구현 전에 함께 정할 사항 |
| --- | --- | --- |
| 그림체 융합 | 유용한 기능으로 유지. 다른 기능을 만든 뒤 구현. A/B 비율 지정과 3개 이상 원본 지원 | 비율 조작 UI, 성분 합성식, 개수·범위·순서 처리 |
| 여러 Prompt로 탐색 | 2개 이상 Prompt의 생성 결과를 함께 보며 조합 단위로 한 번 선택. 생성 비용 증가 수용 | 한 표를 기존 Vote/Selection·부모 선정에 연결하는 검증 |
| 성분 차이와 탐색 제어 | A/B의 작가·LoRA·Weight 차이를 알아보고 향후 사용할 성분을 제어 | 차이 표시 UI, 제외 범위·부모 적격 처리, Blind와의 전환 |

여러 Prompt 탐색과 차이 보기는 초기 비교·평가 구조를 설계할 때부터 반영합니다. 융합은 삭제된 기능으로 취급하지 않고 후순위의 명시적인 구현 항목으로 남깁니다. 구체적인 화면과 미정 정책은 Human-in-the-loop 과정에서 확인합니다.

## 1. 비율을 정하는 다중 그림체 융합

### 사용 목적과 작업 흐름

기존 Web의 융합은 Mobile보다 Desktop에서 유용했다는 사용 경험을 반영합니다. 선택한 이미지가 대표하는 **작가·LoRA 조합을 비율에 따라 합쳐 새 조합과 이미지를 생성**하는 흐름으로 설계합니다. 예를 들어 `A 70% + B 30%`, `A 50% + B 30% + C 20%`입니다. 이 숫자는 성분을 섞는 비율이며 완성 이미지의 시각적 기여도를 보장하는 수치는 아닙니다.

1. 조합 목록·보관함에서 서로 다른 원본을 2개 이상 고릅니다. 3개 이상도 같은 흐름으로 추가할 수 있어야 합니다.
2. 원본 이미지·이름·성분 Snapshot을 확인하고 원본별 비율을 지정합니다.
3. 생성될 조합의 성분·Weight, 잠금·제외·호환성 충돌과 생성 장수를 미리 봅니다.
4. 등록 Workflow와 선택한 Prompt 조건으로 생성하고 결과를 비교합니다.
5. 결과를 보관하거나 새 후보로 가져옵니다. 원본 조합·이미지·점수는 수정하지 않습니다.

여러 Prompt 탐색을 사용하는 프로젝트에서는 융합 결과도 같은 Prompt Set에 대해 생성·확인할 수 있도록 합니다. 일부 Prompt만 미리 볼 경우 전체 조건 평가가 끝난 후보와 구분합니다.

### UI 후보 — 별도 확인 필요

- Desktop: 원본 선택 영역, 비율 편집 영역, 합성 성분 Preview와 결과 영역을 배치합니다. A/B는 Slider와 숫자 입력, 3개 이상은 원본별 비율 행과 합계 표시를 우선 검토합니다.
- Mobile: 원본 Card를 세로로 쌓고 숫자 입력·증감 버튼으로 비율을 조정합니다. Drag나 Hover 없이 추가·제거·비율 조정이 가능해야 합니다.
- 원본을 추가·제거하거나 한 비율을 바꿀 때 나머지를 어떻게 재분배할지는 구현 전에 확인합니다. 합계 100%를 직접 맞추는 방식과 상대 비중을 정규화하는 방식을 몰래 혼용하지 않습니다.
- 여러 비율을 한꺼번에 생성하는 탐색 UI는 추가 제안입니다. 이번 요구만으로 자동 생성 범위를 늘리지 않습니다.

기존 2개 융합 화면에 Slider만 추가하면 충분하다고 가정하지 않습니다. 3개 이상 원본의 선택·수정·결과 추적까지 포함해 새 화면안을 확인합니다. 이 화면 검토는 융합 구현 차례에 진행하며 0단계에서 전체 융합 도구를 만들지 않습니다.

### 성분 합성의 설계 후보

다음은 확정 산식이 아닌 설명·검증을 위한 후보입니다. 원본 비중을 음수가 아닌 값으로 받고 합이 0인 입력은 거부합니다. 정규화한 비율을 `alpha_i`라고 하면:

```text
alpha_i = source_ratio_i / sum(source_ratio)
merged_weight(component) = sum(alpha_i * source_weight_i(component))
```

한 원본에 없는 성분은 해당 원본의 기여를 0으로 두고, 공통 성분은 Identity 기준으로 합칩니다. 예를 들어 A에만 Weight 1.0인 성분이 있으면 70:30 합성의 제안 Weight는 0.7입니다. LoRA Model/CLIP Strength는 각각 계산합니다.

이 방식은 기존의 `고유 성분 유지 + 겹친 Weight 평균`과 다를 수 있습니다. 합성 전후 표로 차이를 확인한 뒤 선택해야 합니다. 원본에만 있는 성분을 비율만큼 낮출지 등도 미정 사항입니다.

최소한 다음을 확인해야 합니다.

- A 100%/B 0%에서는 B의 성분이 새로 들어가지 않고 A의 구성·순서·Weight를 재현합니다. 50:50은 공통 성분과 각 원본의 고유 성분 처리까지 검증합니다.
- 같은 LoRA 이름이라도 파일 Identity·Hash가 다르면 같은 성분으로 합치지 않습니다. 독립 Strength, 0, 성분의 부재와 비활성 상태를 구분합니다.
- 다중 LoRA의 적용 순서, 소수 정밀도·반올림·0 성분 제거, 최대 성분 수와 범위 초과 처리를 명시합니다. 합성 후 자동 Clamp·성분 제거로 비율 의미를 바꾸지 않습니다.
- 현재 프로젝트의 잠금·제외 규칙과 충돌하면 Preview에서 해결하게 합니다. 실험과 일반 후보 채택의 제약을 구분합니다.
- 최초에는 같은 모델·Workflow·평가 조건의 원본을 대상으로 하는 안을 제안합니다. 다른 프로젝트·조건 원본을 허용하는 범위는 별도로 확인합니다.
- 결과는 새 Candidate로 평가합니다. 원본 Elo를 비율 평균해 물려주지 않습니다. 이미 존재하는 동일 조합이면 중복 사실과 재사용 가능 여부를 표시합니다.

저장할 출처는 원본 조합 Snapshot, 입력 비율과 정규화 비율, 합성 정책 Version, 실제 합성 성분·순서, RenderPlan과 결과입니다. 원본이 나중에 수정·삭제돼도 무엇을 섞었는지 해석할 수 있어야 합니다.

## 2. 여러 Prompt를 함께 보는 일상 탐색

### 기존 계획과 달라지는 점

단일 Prompt에서만 비교·진화하면 그 Prompt에만 맞는 조합이 선택되고, 다른 Prompt에서는 결과가 무너질 수 있다는 사용 경험에서 출발합니다. **여러 Prompt의 결과를 함께 보면서 평소 선별과 유전 알고리즘의 선택 근거를 쌓는 기능**을 구상합니다. 생성 시간이 Prompt 수에 따라 늘어나는 비용은 감수할 수 있다는 사용자 의사를 반영합니다.

| 기능 | 목적·사용 시점 |
| --- | --- |
| 여러 Prompt 탐색 | 처음부터 2개 이상 Prompt의 결과 묶음으로 조합을 비교하며 반복 진화 |
| 17번 Prompt 재시험 | 현재 조합을 유지한 채 Prompt 또는 Prompt Set 변경 결과를 시험·채택 |
| 19번 검증 세트 | 최종 후보·보관 스타일을 별도 Case·Seed에서 검증하며 원본 순위를 자동 변경하지 않음 |

따라서 이 요구를 P1의 최종 검증 세트만으로 충족했다고 처리하지 않습니다. 단일 Prompt 사용도 지원하되, 임시로 한 Prompt만 구현한 중간 상태를 여러 Prompt 탐색 완료로 표시하지 않습니다.

### 평가 범위와 생성 조건

설계안의 `Prompt Set`은 이름·순서·안정적인 Case ID가 있는 Prompt 목록의 불변 Version입니다. 각 Case에는 Positive/Negative와 필요한 입력, 전개 결과·Seed 참조를 기록합니다. 공통 Workflow·모델·Sampling 조건과 함께 한 평가 계약을 구성합니다.

- 후보 A와 B는 **같은 Prompt Set의 동일 Case·Seed끼리** 대응시킵니다. `A의 Prompt 1`과 `B의 Prompt 2`를 승패 Pair로 연결하지 않습니다.
- 각 후보의 성분·Weight는 모든 Case에서 동일합니다. 후보별로 유리한 Prompt만 선택하거나 Case마다 성분을 다시 뽑지 않습니다.
- Wildcard·무작위 Tag는 Case별로 공통 전개해 후보 A/B에 공유합니다. Case 사이에까지 동일 텍스트나 같은 Seed를 강제한다는 뜻은 아닙니다.
- Prompt의 추가·삭제·수정, 비교 대상 구성이나 집계 정책 변경은 평가 의미를 바꿉니다. 새 평가 계약과 고정 조합 재시험을 사용하며 과거 점수를 조용히 재해석하지 않습니다.
- 생성 장수는 `후보 수 × Prompt 수 × Seed 수 - 정확히 일치하는 재사용 Render 수`로 계산합니다. 예: 후보 12개×Prompt 3개×Seed 1개는 재사용이 없으면 36장입니다. 시간·VRAM 증가량을 장수만으로 단정하지 않습니다.
- 생성 전 신규 장수를 보여주고 완료·실패·미확인 상태를 Case별로 관리합니다. 실패한 항목만 재시도하며 접속 복구 때 자동 중복 제출하지 않습니다.

Render를 Candidate당 한 장으로 가정하지 않습니다. 각 Render에는 Prompt Set Version·Case ID·Seed·실제 조건 Snapshot과 소유 관계가 필요합니다. 복원·분기·보관·Export에도 해당 결과 묶음의 참조를 포함합니다. 구체적인 테이블 이름은 구현 단계에서 결정합니다.

### 비교 UI 후보

- Desktop: 행은 Prompt, 열은 조합 A/B인 Matrix를 우선 검토합니다. 같은 행에서 구도·결과를 비교하고 전체 묶음을 보고 판단할 수 있게 합니다.
- Mobile: 현재 Prompt의 A/B를 나란히 또는 한 장씩 보고, Case 전환·세로 목록으로 다른 Prompt 결과를 확인하는 안을 검토합니다. 현재 Case와 전체 결과 확인 상태를 표시합니다.
- A/B의 의미와 좌우 위치는 Case를 바꿔도 유지합니다. 긴 이미지 목록 때문에 투표 버튼이나 성분 차이 보기가 사라지지 않게 합니다.
- 일부 Case가 실패했거나 아직 보지 않았다면 완전한 묶음처럼 표시하지 않습니다. 필수 이미지 준비·확인 정책과 부분 결과로 투표할 수 있는지는 0단계 및 비교 구현에서 확인합니다.

### 투표·Elo·진화 — 조합 단위 한 번 선택

2026-11-10 Phase 0 피드백으로 **모든 Prompt를 함께 보고 조합 A/B/비슷함을 한 번 선택**하는 방식으로 확정했습니다. Prompt별 투표와 방식 토글은 제거합니다. 한 Match가 Prompt Set 전체의 같은 조합 A/B를 가리키고 Elo·Selection·성분 통계에 한 번 반영됩니다. 이미지 수만큼 같은 승리를 중복 가산하지 않습니다.

일반 Elo·Placement·Evolution Selection 각각의 기존 의미, 부모 점수 고정·Skip·Undo 계약을 유지합니다. 서로 다른 평가 구간이나 최종 검증의 점수를 임의 합산하지 않습니다. 현재 프로젝트·다른 프로젝트 열람 범위와 설정 경계는 [21번 문서](21_project_context_settings_and_fork.md)를 따릅니다.

성분 점수 추정도 같은 근거를 Prompt 수만큼 복제해 새 관측 수를 늘리지 않습니다. 대표 점수와 Case별 관측을 구분하고, 정책을 확정하기 전 다중 Prompt의 진화 성능이 검증됐다고 보고하지 않습니다.

### 재시험·복원과의 연결

17번의 고정 조합 재시험은 단일 Prompt 변경 외 Prompt Set 변경에도 적용합니다. 원본 후보의 성분·Weight·출발 세대를 유지하고 새 Set의 결과 묶음을 생성합니다. Trial 평가·Drop·채택과 원본 보존 원칙은 유지합니다.

Checkpoint에는 당시 Prompt Set·투표/집계 정책 Version과 모든 Case Render 참조를 포함합니다. 세대 복원 Preview는 삭제 후보 수와 이미지 수를 구분하고 이후 Case별 이미지·Vote를 빠뜨리지 않습니다. 독립 분기·채택 구간의 유효 참조는 기존 경계대로 보호합니다.

## 3. 비교에서 성분 차이를 보고 Search Space 줄이기

### 보여줄 차이

현재 Web은 작가·LoRA 조합이 긴 한 줄로 표시돼 무엇이 달라졌는지 따라가기 어렵다는 사용 경험을 반영합니다. 비교 화면에 **차이만 보기**와 전체 성분 보기를 제공합니다. 긴 문자열을 직접 눈으로 대조하지 않아도 변경점을 확인할 수 있어야 합니다.

| 분류 | 표시 예시 |
| --- | --- |
| A에만 있음 | 작가 X STR 0.8, LoRA Y STR 0.6 |
| B에만 있음 | LoRA Z STR 0.4 |
| 강도 변경 | 공통 LoRA Y: STR 0.6 → 0.9 |
| 동일 | 같은 Identity·Weight의 공통 성분. 접어서 확인 가능 |
| 그 밖의 차이 | LoRA 파일 Hash, 적용 순서, 활성 상태, Trigger 정책 차이 |

작가와 LoRA를 나눠 행 단위로 표시하고 화면의 강도 표시는 STR로 통일합니다. 2026-11-17 [CLIP 고정 정책](lora_clip_strength_policy.md)에 따라 앞으로 생성·새 등록하는 LoRA는 CLIP 1을 사용합니다. 과거 Snapshot은 소급 수정하지 않습니다. 빠진 성분·비활성 항목은 구분합니다.

방향 없는 A/B 대조에서는 `A에만/B에만`을 사용합니다. 부모→자녀처럼 실제 출처가 있는 경우에만 `추가/제거/변경`과 어느 부모 대비인지 표시합니다. Crossover의 여러 부모도 구분합니다. 현재 Catalog 값으로 과거 조합을 재구성하지 않고 비교 대상의 불변 Snapshot을 사용합니다.

**차이는 관측 정보이며 인과관계의 확정이 아닙니다.** 여러 성분이 함께 달라졌다면 특정 LoRA가 패배 원인이라고 자동 표시하지 않습니다. 필요한 경우 19번 Ablation으로 단일 변경을 추가 확인할 수 있게 연결합니다.

### 차이 보기에서 설정 제어로 연결

성분 행에서 `앞으로 이 프로젝트의 새 조합에 사용하지 않기`와 재허용으로 이어지는 흐름을 제안합니다. 목적은 사용자가 판단한 불필요한 성분을 제외해 Search Space를 줄이는 것입니다.

- 기본 범위는 현재 프로젝트의 **향후 후보 생성**으로 제안합니다. 전체 Catalog 삭제나 다른 프로젝트의 사용 중단과 구분해 UI에 범위를 표시합니다.
- Random뿐 아니라 Mutate의 상속·추가·교체와 Crossover에도 적용해야 합니다. 제외 성분을 부모에서 그대로 가져와 새 자녀에 재등장시키지 않습니다.
- 기존 Candidate·Render·Elo·Vote·보관 결과는 그대로 둡니다. 기존 후보의 평가 제외나 Drop은 별도 명시 동작입니다.
- 제외 성분이 포함된 부모의 처리와 생성 계획을 보여줍니다. 잠금과 제외가 충돌하면 사전 검증으로 해결하게 하고 몰래 잠금을 풀지 않습니다.
- 성분 제외가 해당 LoRA의 품질 불량·로딩 실패·통계적 유해성을 자동 판정했다는 뜻은 아닙니다. 선택 이유를 Memo로 남길 수 있습니다.
- 제외 정책을 Revision으로 기록하고 해당 계획에 고정합니다. 생성 중 정책 변경은 이미 제출한 조합을 수정하지 않으며 이후 계획부터 적용합니다.
- 고정 조합 재시험은 원본을 재현하는 별도 동작입니다. 제외 때문에 Weight·성분을 몰래 바꾸지 않고 해당 성분 포함 사실을 표시해 실행 여부를 판단하게 합니다.

Desktop은 A/B 아래 또는 옆의 정렬된 차이 표, Mobile은 접을 수 있는 차이 목록과 성분 상세 Sheet를 검토합니다. 이미지 영역을 불필요하게 축소하지 않습니다.

Blind에서는 성분 이름·Weight·차이 표도 가립니다. 투표 후 확인 또는 명시적 Blind 해제 후 제어하도록 하며, 숨긴 성분 이름을 버튼·Tooltip으로 노출하지 않습니다. 이름을 보기 위해 Blind를 해제할 때 이미지를 다른 Pair로 교체하지 않습니다.

## Human-in-the-loop 확인과 수락 기준

| 확인 시점 | 사용자가 볼 것 | 개발자가 확인할 것 |
| --- | --- | --- |
| 0단계 | 현재 Web 기준으로 유지할 조작, 다중 Prompt 비교안, 성분 차이 보기 위치 | 기존 목업이 새 요구를 이미 구현했다고 오해시키지 않기 |
| 실제 생성·비교 단계 | 같은 두 조합의 2개 이상 Prompt 결과와 비용, 차이 목록·제외 범위 | Case별 대응·Seed/성분 고정, 장수, 실패 재시도, 중복 Vote 방지 |
| 진화 전 | 여러 Prompt 평가가 어떤 부모 선택 근거가 되는지 | 확정한 투표·집계 정책과 Selection·성분 통계의 일관성 |
| 차이 기반 제외 후 | 제외한 성분의 재등장 여부와 기존 후보 보존 | 세 생성 방식·상속·잠금 충돌, 다른 프로젝트 비영향 |
| 후순위 융합 차례 | 비율 UI부터 확인한 뒤 2개 및 3개 이상 원본의 실제 결과 | 100:0·50:50·50:30:20, 공통/고유 성분·독립 Strength·출처·중복 처리 |

다중 Prompt 수락 검증에는 다음을 포함합니다.

- A/B×Prompt 2개×Seed 1개에서 재사용이 없으면 4장, 서로 대응하는 Case끼리 표시합니다.
- Case를 바꿔도 A/B가 뒤바뀌지 않고, 단일 Prompt 사용도 가능합니다.
- 일부 실패·미확인·필수 Case 누락을 완전한 비교로 처리하지 않습니다.
- 투표 정책을 확정한 뒤 Match·Elo·Selection·Undo·성분 관측 수가 그 정책과 일치합니다.
- Set 변경 재시험은 원본 통계·조합·세대를 보존합니다. 복원·분기·보관에서 모든 Case Asset을 추적합니다.

차이 보기와 융합도 실제 사용 확인 전 완료로 표시하지 않습니다. 이번 변경은 문서화이며 0단계 목업 제작·서비스 변경·생성 실행을 시작하지 않습니다.

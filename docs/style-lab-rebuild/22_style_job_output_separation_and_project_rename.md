# 스타일 구성 작업·출력 분리와 프로젝트 이름 변경

2026-11-10 사용자 결정입니다. 실제 생성 연결 전에 정한 요구사항이며, 이 문서 작성으로 API·DB·파일 이동이 구현된 것은 아닙니다.

## 확정한 분리 규칙

| 항목 | 규칙 |
| --- | --- |
| 생성 기반 | CHS의 등록 Workflow·Job·Output 추적을 재사용 |
| 작업분류 | `모델명 / 프로젝트명`에 자동 배정 |
| 작업 메모 | `세대003-01 이미지 생성`처럼 세대부터 작성. 모델명·프로젝트명은 넣지 않음 |
| 실제 출력 | `from_comfy_home_style/모델명/프로젝트명/…`의 스타일 구성 전용 루트 |
| 출력 형식 | 등록 Workflow의 기존 출력 설정을 따름. WebP를 요구하거나 자동 변환하지 않음 |
| 일반 작업 탭 | `스타일 구성 작업도 보기` Checkbox, 기본 해제 |
| 일반 이미지·결과물 탭 | `스타일 구성 이미지도 보기` Checkbox, 기본 해제 |
| 프로젝트 이름 변경 | 웹에서 변경하면 표시명·출력 폴더명·해당 작업분류명도 함께 변경 |
| 수동 이동 | 스타일 구성에서 생성한 작업의 분류 변경과 출력 폴더 이동을 금지 |

WebP는 사용자가 확장자를 기억하지 못해 제시한 예시입니다. 포맷 변경 요구로 해석하지 않습니다. 조사한 Anima 등록본은 PNG이며, 다른 Workflow도 각자 실제 설정을 따릅니다.

작업 메모에 모델·프로젝트명을 넣자는 앞선 제안과 프로젝트 이름 변경 후 기존 폴더를 유지하자는 제안은 이 결정으로 대체합니다. 이름 변경을 이유로 과거 작업의 메모를 일괄 수정하지 않습니다.

## 식별과 표시 이름의 분리

작업·요청·출력에 생성 출처와 Project/Evaluation/Generation/Candidate/Render 소속을 저장합니다. 스타일 구성 여부는 수정 가능한 메모·분류명·경로 문자열만으로 판정하지 않습니다.

- 생성 출처는 일반 생성과 스타일 구성을 구분합니다. 메모 수정이나 프로젝트 이름 변경으로 출처가 바뀌지 않습니다.
- Project ID·분류 ID·Output ID 등 소유 관계는 이름을 바꿔도 유지합니다. 동명 프로젝트나 이름 재사용으로 다른 프로젝트의 작업을 합치지 않습니다.
- 분류와 출력 폴더는 프로젝트에 연결해 관리하며, 화면에 보이는 모델·프로젝트 이름을 반영합니다. 파일명에 사용할 수 없는 문자와 동명 충돌은 생성·이름 변경 시 검증합니다.
- 프로젝트 표시명 변경은 평가 조건 변경이 아닙니다. 새 Evaluation을 만들거나 이미지 재생성·Elo 변경·세대 증가를 유발하지 않습니다.

## 작업과 파일의 이름

작업 한 건에 여러 조합·Prompt의 이미지가 포함될 수 있습니다. `세대003-01`의 `01`은 해당 세대의 생성 작업 회차로 사용하며, 개별 파일의 조합 번호와 구분합니다. 상세한 작업 종류는 세대 뒤에 표현할 수 있으나 모델명·프로젝트명을 메모에 반복하지 않습니다.

파일은 여러 Prompt와 재생성을 구분하고 세대 복원 후 같은 번호를 다시 사용해도 덮어쓰지 않아야 합니다. 예를 들면 다음과 같습니다. 확장자는 해당 Workflow가 실제로 저장한 형식입니다.

```text
from_comfy_home_style/
  Anima/
    프로젝트명/
      세대003-조합01-Prompt01-RenderID.png
      세대003-조합01-Prompt02-RenderID.png
      세대003-조합02-Prompt01-RenderID.png
```

고유 식별자는 프로젝트 동명 구분과 Render 충돌 방지에 사용합니다. 구체적인 경로 정규화·식별자 표기는 실제 저장 구현에서 정하되, 프로젝트 이름 변경이 폴더명에도 반영되어야 한다는 요구는 유지합니다. Seed가 여러 개면 Render 소속과 파일명 정책에서 구분합니다.

2026-11-11 사용성 보완에서는 화면도 `세대001-조합01`처럼 이 규칙을 따릅니다. 새 조합 번호는 같은 프로젝트·세대의 생성 묶음 사이에서 이어지고, Job 메모의 회차는 각 세대의 `01`부터 시작합니다. 기존 파일은 재작성하지 않습니다. 상세는 [그림체 관리·Viewer 개선 기록](style_usability_review.md)을 참고합니다.

## 웹에서 프로젝트 이름 바꾸기

프로젝트 이름 변경은 프로젝트가 소유한 출력 폴더의 Rename과 작업분류명 변경을 함께 수행하는 관리 동작입니다. 다른 프로젝트나 일반 생성 분류를 이름 문자열 검색으로 찾아 변경하지 않습니다.

1. 변경 대상 Project와 현재 Revision, 연결된 분류·출력 폴더를 확인합니다.
2. 새 이름의 경로 유효성·충돌·파일 잠금·진행 중 생성 여부를 확인합니다. 최초 구현은 관련 생성·복원·다른 Rename이 진행 중이면 완료 후 변경하도록 합니다.
3. 프로젝트 출력 폴더를 Rename하고 같은 분류 ID의 이름을 갱신합니다. 복수 출력 위치가 프로젝트에 연결돼 있다면 대상 전체를 추적합니다.
4. Output Catalog, 요청 결과의 출력 경로, 이미지 조회·보관·Checkpoint·Asset Manifest 등 실제 파일을 찾는 참조를 갱신하거나 안정적인 Asset ID를 통해 새 위치로 해석합니다. Thumbnail 등 경로 기반 Cache도 무효화·갱신합니다.
5. 작업 메모·투표·Elo·세대·성분 구성은 유지하고 변경 결과를 화면에 표시합니다.

DB와 파일 시스템의 변경은 하나의 Transaction이 아니므로 Rename Operation의 이전/새 경로와 진행 상태를 기록해 중단·재시작 후 복구합니다. 일부만 바뀐 상태를 성공으로 표시하지 않으며 중복 요청으로 다시 이동하지 않습니다.

과거 Workflow·평가 조건·생성 출처 Snapshot은 당시 기록으로 보존합니다. 파일 위치 변경을 이유로 이미지 내부 Metadata나 과거 생성 Graph를 재작성하지 않습니다. 실제 파일 접근은 현재 Asset 위치를 해석하며, 오래된 Snapshot의 경로만으로 실패하거나 새 위치에 중복 생성하지 않습니다.

Fork 등 다른 프로젝트에서 같은 물리 이미지를 참조하면 Rename 뒤에도 유효 참조를 유지합니다. 프로젝트 표시명 변경이나 세대 복원이 다른 프로젝트의 출처·결과를 훼손하지 않도록 [15번의 Asset 보호](15_generation_restore_and_deletion.md)와 함께 검증합니다.

## 사용자가 임의로 이동하지 못하게 하기

프로젝트가 관리하는 분류·파일 배치를 유지하기 위한 제한입니다. 다음 동작을 UI와 서버 API 양쪽에서 막습니다.

- 스타일 구성 Job의 작업분류 변경과 다른 분류로의 이동.
- 스타일 구성 출력 파일의 다른 폴더 이동. 일반 결과물 화면에서 실행하는 이동도 포함.
- 연결된 프로젝트 분류·출력 폴더의 개별 이름 변경이나 상위 폴더 이동으로 우회하는 동작. 프로젝트 이름 변경은 스타일 구성의 프로젝트 관리에서 수행.
- 일반 작업·파일과 섞인 일괄 이동은 사전 검증 후 전체 요청을 거부하고 제한 대상을 안내. 일부만 조용히 이동하지 않음.

프로젝트 이름 변경에 따른 관리 Rename은 이 제한의 예외입니다. 같은 프로젝트 소속을 유지하며 사용자 임의 이동과 별도 Service에서 처리합니다. 외부 파일 관리자의 수동 조작을 운영체제 차원에서 막는 기능을 뜻하지 않습니다. 삭제·보관·세대 복원은 각 기능의 별도 계약을 따릅니다.

## 작업·이미지 탭의 표시 범위

Checkbox는 일반 작업·이미지 탭에서 스타일 구성 데이터를 포함할지 결정하며 선택 상태를 보존합니다. 스타일 구성의 프로젝트 화면에서는 해당 프로젝트 결과를 정상 조회합니다.

필터는 서버 조회에 적용해 목록·총건수·페이지 수·분류별 표시 건수·Preview 이전/다음·전체 선택·일괄 처리 대상의 범위를 일치시킵니다. 화면에서 카드만 숨겨 보이지 않는 이미지가 일괄 처리에 포함되게 하지 않습니다. 이 필터는 실행 중 Job 감시·완료 추적을 중단하지 않습니다.

출력 루트는 CHS가 정식으로 관리·조회·보호할 수 있어야 합니다. 기존 단일 관리 루트 전제와 Docker Mount, History 출력 수집, Catalog Sync, 다운로드·Cache·파일 이동 검증을 함께 보강합니다. 일반 출력 경로를 바꾸거나 임의의 외부 경로 접근을 허용하는 방식으로 해결하지 않습니다.

## 구현 단위와 수락 기준

1단계 프로젝트 저장에서는 변경 가능한 표시명과 안정적인 소유 ID, 자동 분류·출력 위치의 연결 및 Rename Operation 경계를 준비합니다. 2단계 실제 생성 연결에서는 자동 분류·메모·출력 경로, 일반 화면의 표시 필터와 이동 제한을 실제 Job·이미지로 완성합니다. 실제 폴더가 생긴 이후 프로젝트 이름 변경도 이 단계에서 검증합니다.

- 스타일 구성 작업이 지정한 모델/프로젝트 분류에 생기고 메모는 세대부터 시작합니다.
- 현재 Workflow 출력 형식과 Metadata를 보존하며 조합·Case·재생성별 파일 충돌이 없습니다.
- Checkbox 기본 해제 시 일반 화면의 목록과 일괄 처리 범위에서 제외되고, 켜면 다시 확인할 수 있습니다.
- 웹에서 이름을 바꾸면 프로젝트 표시명·폴더명·분류명이 일치하고 이전 이미지·작업 상세·보관·Checkpoint 참조가 계속 열립니다. 작업 메모는 그대로입니다.
- 같은 이름·잘못된 경로·파일 잠금·진행 중 작업·중복 요청·재시작 후 복구를 검증합니다.
- UI·직접 API·일괄 이동에서 스타일 구성 Job과 출력의 임의 이동을 막고 일반 작업의 기존 이동 기능을 보존합니다.
- 프로젝트 Rename 후에도 세대 복원·Fork의 공유 Asset 보호와 독립성이 유지됩니다.

실제 구현·검증·사용자 확인 상태는 [개발 과정](development_process.md)에 별도로 기록합니다.

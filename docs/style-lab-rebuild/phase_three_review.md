# 3A단계: Random 초기 조합 생성

2026-11-10. 사용자 승인에 따라 초기 조합 추첨을 연결했습니다. 3단계 중 **Random 초기 조합 → 생성 장수 확인 → 생성**이 이번 범위입니다. 공통 성분 잠금, Mutate/Crossover, 투표·Elo·Undo는 후속 단계입니다. 기존 검토한 그림체 카드·Viewer·여러 Prompt 스크롤 선별을 유지합니다.

## 사용자 확인 순서

1. Home의 **스타일 구성 → 프로젝트 → 이미지 생성**을 엽니다.
2. 먼저 프로젝트 설정의 Prompt, Workflow, 해상도, Seed, 작가·LoRA 허용 여부, 종류별 최소·최대 사용 개수와 STR 범위를 확인·저장합니다. 저장하지 않은 초안은 추첨에 사용하지 않습니다.
3. **Random 초기 조합**에서 조합 수를 입력합니다. 기본 4개이며 한 번에 1~32개입니다. `조합 수 × Prompt 수`로 최대 예정 장수를 표시합니다.
4. **이미지 생성**을 누르면 내부에서 조합을 준비한 뒤 **이미지를 생성할까요?** 확인창에 조합 수 × Prompt 수와 실제 생성 장수만 표시합니다. 성분 목록·STR·추첨 Seed를 펼쳐 보여주는 Preview 화면은 제거했습니다. 이 시점에는 Job·Request·출력 이미지를 만들지 않습니다.
5. **확인**을 누르면 바로 생성을 접수합니다. **취소**나 Escape는 생성하지 않으며, 다시 누르면 같은 준비 조합을 사용합니다. 이전에 준비한 미제출 계획도 현재 설정·요청 개수와 같으면 자동으로 재사용합니다. 미제출 Preview 목록을 별도 화면에 표시하지 않습니다.
6. 결과는 **그림체**의 조합별 카드로 확인하고, 클릭한 조합 안에서 Prompt 이미지를 이전/다음으로 넘겨 봅니다. **선별**에서는 같은 묶음의 A/B 위치에 놓을 두 조합을 고른 뒤 모든 Prompt를 스크롤하며 비교합니다. Blind 중에는 조합 선택을 비활성으로 하고 이름을 숨깁니다. 실제 투표는 아직 비활성입니다.
7. 실패·취소 항목만 재시도하면 원래 후보·성분·STR·Prompt·Seed를 그대로 사용합니다. 이미 성공한 결과는 다시 생성하지 않습니다. 접수 여부 미확인은 자동 재전송하지 않습니다.

**이번 개입 지점:** 장수 확인 후 원하는 작은 Batch를 직접 생성해 이미지 품질·조합 차이·비교 흐름을 확인합니다. 다음 기능을 일괄 추가하지 않고 이 흐름에 대한 피드백을 먼저 받습니다.

## 추첨 규칙과 저장 경계

- 알고리즘 식별자는 `initial-random-v1`입니다. Elo나 기존 작가/LoRA 점수를 이용한 가중 추첨·진화가 아닙니다.
- 작가와 LoRA 각각에서 `최소 사용 개수 ~ min(최대 사용 개수, 허용된 성분 수)` 중 개수를 균등 추첨합니다. 그 개수만큼 성분을 중복 없이 고른 뒤 STR을 선택합니다. 종류별 0~0은 해당 종류 미사용이며, 둘 다 0이면 기본 모델 조합 하나입니다.
- STR은 **설정 최솟값부터 0.01 간격의 값과 최댓값** 중 균등 선택합니다. 예: 0.4~0.43 → 0.4/0.41/0.42/0.43, 0.401~0.405 → 0.401/0.405. 0.4~0.4는 정확히 0.4입니다. Decimal 계산 후 저장하며 음수·0·좁은 범위도 경계 밖으로 반올림하지 않습니다. 별도 고정 STR Checkbox는 추가하지 않습니다.
- 추첨 Seed는 프로젝트 ID와 Operation ID에서 만들며 프로젝트의 **이미지 Seed와 독립적**입니다. 동일하게 저장된 요청을 재전송하면 기존 계획을 반환합니다. Browser는 통신 실패 시 Operation ID를 유지해 응답 유실 뒤 새로운 조합이 생기지 않게 합니다. 설정 검증·Revision 충돌은 새 요청으로 재확인합니다.
- 계획에 추첨 버전, 추첨 Seed, 원래 개수 범위·허용 성분의 STR 범위, 요청/실제 개수, 시도 횟수, 부족분과 확정 조합을 저장합니다. 계획 조회·실제 제출·실패 재시도에서 Random을 다시 실행하지 않습니다.
- 중복 검사 범위는 **같은 프로젝트의 같은 Evaluation Snapshot**입니다. 실제 생성한 조합과 저장된 미제출 Preview를 모두 포함합니다. 성분 순서·파일 Metadata는 제외하고 실제 STR로 비교합니다. LoRA의 생략한 CLIP은 STR와 같은 것으로 정규화하고 명시적인 다른 CLIP 강도는 구별합니다.
- 요청 조합 수의 30배까지만 추첨합니다. 부족하면 확인창에 요청 개수와 실제 준비된 개수·장수를 표시하고, **실제 준비된 장수만** 제출합니다. 하나도 찾지 못하면 작업 없이 거절합니다. 제한 횟수 안에 찾지 못했다는 뜻이며 전체 검색 공간 소진을 증명했다고 표시하지 않습니다.
- 비동기 Comfy 사전 확인 뒤 DB Transaction에서 Revision·Operation·중복을 다시 검사합니다. 경쟁 Preview가 같은 조합을 먼저 저장하면 409로 거절하여 중복 후보를 남기지 않습니다.
- 기존 고정 조합 검증 도구는 접힌 **고정 A/B 조합 직접 확인**에 남깁니다. Random은 같은 등록 Workflow·Adapter·NegPip·LoRA Loader·출력 분리·관리 Rename 경로를 재사용합니다. 새로운 DB Schema Migration은 없습니다.

## 생성 확인 UI 피드백 반영

사용자가 생성 전 조합 목록을 보여줄 필요 없이 확인만 누르면 생성되기를 요청했습니다. 이 요청이 이전의 조합 상세 Preview 검토 절차를 대체합니다. 서버의 불변 계획·중복 검사·명시적 제출·실패 재시도 정책은 유지하며 UI에서 상세 Preview를 제거했습니다.

- 일반 Random 생성과 기존 고정 A/B 도구, 저장된 미제출 계획 모두 장수 확인창의 **확인**으로 생성합니다. 확인창에는 성분 목록이나 추첨 정보가 없습니다.
- 취소·Escape에서는 Job이 생기지 않고 입력 화면으로 돌아갑니다. 취소 후 다시 누르면 같은 준비 조합을 확인하므로 취소만으로 새 조합을 계속 소비하지 않습니다.
- 생성 장수가 줄어든 경우에도 별도 상세 화면 없이 확인창 안에 실제 개수와 장수를 표시합니다.
- 운영 검증은 확인창 표시와 취소까지만 하며 실제 GPU 제출은 하지 않습니다.

Playwright/Edge의 프로젝트·고정 생성·피드백·그림체 카드·Random 생성 5개 시나리오를 변경 후 다시 통과했습니다. 확인 전 작업 없음, 확인 후 12장 생성, 취소·Escape·새로고침 후 준비 조합 재사용, 성분 목록 없음과 320/390/768/1280px 화면을 검증했습니다.

운영에서도 장수 확인창·취소·Escape를 검증했고 POST 없이 기존 준비 계획을 재사용했습니다. Job 186개·Request 3036개·출력 DB 행 7747개와 프로젝트 설정·기존 스타일 이미지 12장의 SHA256이 동일합니다. 정적 UI만 반영했으며 Python 서비스 재시작은 필요하지 않았습니다. ## Commit 정리와 다음 작업 제안

사용자 요청에 따라 Random 초기 조합 생성과 생성 확인 UI 개선을 함께 Commit합니다. 다음 제안은 3B 공통 성분 유지입니다. 지정한 작가·LoRA는 모든 새 조합에 반드시 포함하고 나머지 성분을 추첨합니다. STR 값 고정은 기존처럼 최소·최대 범위를 같게 설정하며 별도 고정 STR Checkbox를 재도입하지 않습니다. 필수 성분과 사용 개수·허용 여부 충돌을 생성 전에 안내하고, 기존 조합·이미지는 변경하지 않는 단위로 검토합니다. 이후 4A 투표·Elo·Undo 연결을 진행합니다. 이 문단은 다음 작업 제안이며 구현 완료나 착수 승인 기록이 아닙니다.

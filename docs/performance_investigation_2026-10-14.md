# 결과물 목록 조회 성능 실험 기록

## 현재 채택 상태

- 브랜치: `codex/output-loading-performance`
- 비교 baseline commit: `d7fd8fb Improve output listing performance and add stage timing logs`
- `os.scandir()`의 `DirEntry` 정보를 재사용하고, 목록의 파일별 `Path.resolve()`는 제거한 상태입니다.
- 현재는 파일명 metadata로 목록의 `Path.stat()`을 대체한 버전을 적용했습니다. 파일 크기 표시도 제거했으며 구현과 실험 기록을 사용자 요청으로 함께 commit했습니다. 결과는 아래 6번에 기록했습니다.
- 후속 사용자 요청으로 해상도 Cache의 시간 만료를 제거하고 최대 항목 수를 30,000개로 늘렸습니다. LRU와 앱의 파일 이동 시 무효화는 유지합니다. 아래 6번의 측정 당시에는 최대 2,048개와 60초 TTL이 있었으며 추가 변경은 7~8번에 기록했습니다.
- 작업별 조회도 전체 폴더를 탐색한 뒤 DB에 기록된 output path로 필터링합니다. 작업 path만 직접 조회하는 방식은 아직 구현하지 않았습니다.
- `os.walk()` 전환 실험은 전체 조회가 느려져 사용자 요청으로 원복했습니다. 미커밋 변경이었으므로 해당 코드·테스트 3개 파일을 `d7fd8fb` 상태로 복원했고 commit history는 변경하지 않았습니다.
- DB 조회 최적화와 썸네일·원본 전송의 `stat()`은 이번 변경 범위 밖입니다.

## 환경과 측정 범위

- 측정일: 2026-10-14
- 실제 서버: Windows Docker Desktop의 Docker Compose, Linux Python 3.13 container, Windows output 폴더의 bind mount
- 데이터: 관리 파일 2,004개, 디렉터리 항목 3개, 비교 작업의 결과물 70개
- 목록 API: `GET /api/outputs?page=1&page_size=24`, 작업 조회는 `job_id` 추가
- 브라우저 Network 시간, 서버의 `perf_counter()` 단계별 시간, 동일 프로세스에서의 파일 탐색 비교를 구분했습니다.
- 안정 상태의 브라우저 비교는 썸네일 Warmup 완료 후 수행했고 최초 이미지 크기 Cache miss가 있는 예비 조회는 제외했습니다.
- 파일 탐색 비교에는 탐색·파일 종류 또는 확장자 확인·작업 필터·`stat()`·정렬이 포함됩니다. DB mapping, 이미지 크기 읽기, HTTP 직렬화는 포함하지 않습니다.
- Python API 호출 횟수와 실제 filesystem system call 횟수는 다릅니다. `DirEntry`의 종류 확인은 이미 얻은 정보를 재사용할 수 있고, `resolve()`는 한 호출 안에서도 여러 filesystem 조회를 수행할 수 있습니다.

요청 ID, 단계별 시간·호출 횟수, 독립 비교의 원시 표본은 [JSON 측정 기록](performance/output_listing_experiments_2026-10-14.json)에 보관했습니다. `runtime/`은 Git에서 제외되므로 장기 기록은 이 문서와 JSON을 기준으로 합니다.

## 1. 초기 병목 진단과 timing log 추가

썸네일 Cache가 있어도 전체 목록 API는 약 7.31~7.39초, 작업 결과 70~100개 조회는 약 5.65~5.70초였습니다. 초기 구현은 `rglob()` 결과에 `Path.is_file()`, `Path.resolve()`, `Path.stat()`을 수행했습니다.

Warmup 완료 후 마지막 반복 조회의 서버 측 누적 시간입니다.

| 단계 | 전체 조회 | 작업 결과 70개 |
|---|---:|---:|
| 파일 목록 나열 | 33.878ms | 24.290ms |
| `is_file()` 및 확장자 확인 | 1,800.153ms | 1,813.400ms |
| `resolve()` 및 관리 경로 확인 | 3,214.247ms | 3,241.515ms |
| 별도 `stat()` | 1,770.385ms | 61.375ms |
| DB output mapping | 468.218ms | 451.888ms |
| 전체 응답 준비 | 7,374.554ms | 5,682.643ms |

두 조회 모두 `is_file()`은 2,007회, `resolve()`는 2,004회였습니다. 별도 `stat()`은 전체 2,004회, 작업 70회였습니다. 파일 목록 나열보다 파일별 속성·경로 확인의 누적 비용이 컸습니다.

썸네일 Cache hit 요청의 응답 준비는 3.6~9.4ms, Cache 조회 자체는 최대 0.09ms였습니다. 처음 읽은 페이지의 이미지 크기 확인은 24개에 약 655~658ms가 추가됐지만 반복 조회에서는 약 0.15ms였습니다.

`OUTPUT_TIMING` 로그를 추가했습니다. 응답의 `X-Output-Timing-Id`로 같은 요청을 연결하며, 단계별 호출 수·누적 시간·최대 시간과 전체 응답 준비 시간을 기록합니다. 상위 단계는 하위 단계 시간을 포함하므로 모든 `total_ms`를 더하면 중복 계산됩니다.

## 2. Path.is_file 대신 DirEntry 정보 재사용

`rglob()`의 `Path`를 받은 뒤 종류를 다시 확인하는 방식에서, `scandir()`의 `DirEntry`를 유지하고 `DirEntry.is_file()`을 사용하는 방식으로 변경했습니다. `resolve()`, 별도 `Path.stat()`, DB 조회, 전체 탐색 후 작업 필터는 유지했습니다.

같은 탐색 순서에서 종류 확인 API만 바꾼 독립 비교입니다.

| 조회 | 확인 API | 종류 확인 누적 | 탐색 전체 |
|---|---|---:|---:|
| 전체 | `Path.is_file()` | 1,031.388ms | 3,707.716ms |
| 전체 | `DirEntry.is_file()` | 20.151ms | 2,675.610ms |
| 작업 70개 | `Path.is_file()` | 1,012.658ms | 2,702.197ms |
| 작업 70개 | `DirEntry.is_file()` | 8.699ms | 1,719.179ms |

독립 효과는 전체 약 1,032ms, 작업 약 983ms 감소였습니다. 브라우저 요청의 종류 확인 단계는 약 1.8초에서 2.6~3.6ms로 감소했습니다. 당시 브라우저 전체 응답 감소에는 다른 filesystem 작업 시간의 변화도 포함됐으므로 전체 감소분을 종류 확인 API의 효과로만 해석하지 않습니다.

두 방식의 파일 경로·크기·수정 시각 결과가 같음을 확인했습니다. 결과: **채택**.

## 3. 목록의 파일별 resolve 제거

Symlink를 사용하지 않는 운영 전제를 바탕으로 목록의 파일별 `resolve()`를 제거했습니다. 탐색 방식, 필터 순서, `stat()`, DB 조회는 유지했습니다.

동일한 파일 종류 확인·필터·`stat()` 조건에서 `resolve()` 여부만 바꾼 비교입니다.

| 조회 | `resolve()` | 호출 수 | `stat()` 호출 수 | 탐색 전체 |
|---|---|---:|---:|---:|
| 전체 | 수행 | 2,004 | 2,004 | 2,781.958ms |
| 전체 | 생략 | 0 | 2,004 | 1,107.822ms |
| 작업 70개 | 수행 | 2,004 | 70 | 1,738.886ms |
| 작업 70개 | 생략 | 0 | 70 | 65.163ms |

독립 비교에서 두 조회 모두 약 1.67초 감소했고 반환 경로·크기·수정 시각이 같았습니다. 실제 브라우저 응답은 전체 3.25초에서 1.57~1.59초, 작업 2.22초에서 0.62~0.67초로 감소했습니다.

결과: **채택**, `DirEntry` 변경 및 timing log와 함께 `d7fd8fb`에 commit했습니다. 제거 범위는 목록의 파일별 경로 해석이며 다른 파일 접근 API의 구현을 함께 변경한 실험은 아닙니다.

## 4. os.walk 도입과 명시적 is_file 생략

`d7fd8fb`를 baseline으로, `os.walk()`가 반환하는 `filenames`에서 `Path`를 생성하는 버전을 구현했습니다. 목록의 명시적인 `is_file()`·`is_dir()` 및 별도 Symlink 검사는 추가하지 않았습니다. `stat()`, DB 조회와 작업 필터는 유지했습니다. 운영 전제는 Symlink를 만들지 않는 것입니다.

### 브라우저 비교

각 조건 5회 측정했습니다. 표는 평균입니다.

| 조회 | 기존 `scandir` | `walk` | 관찰 |
|---|---:|---:|---|
| 전체 2,004개 | 1,579.741ms | 2,346.967ms | 약 48.6% 느려짐 |
| 작업 결과 70개 | 628.040ms | 628.734ms | 평균은 거의 동일 |

작업 조회의 `walk` 표본 중 첫 요청은 774ms, 나머지는 585~600ms였습니다. 제한된 5회 표본의 변동을 고려해 명확한 작업 조회 성능 향상으로 판단하지 않았습니다.

### 동일 프로세스의 교차 비교

두 탐색 구현을 같은 Docker 프로세스에서 각 5회 실행하고, 라운드마다 순서를 번갈아 바꿨습니다. 모든 실행에서 전체 경로·크기·수정 시각 결과가 같음을 확인했습니다.

| 조회 | 기존 탐색 평균 | `walk` 탐색 평균 | 기존 / `walk`의 명시적 `is_file()` 횟수 | `stat()` 횟수 |
|---|---:|---:|---:|---:|
| 전체 | 1,078.579ms | 1,851.191ms | 2,007 / 0 | 둘 다 2,004 |
| 작업 70개 | 63.251ms | 91.206ms | 2,007 / 0 | 둘 다 70 |

### 단계별 관찰

브라우저 요청의 서버 로그에서 전체 조회의 `stat()` 누적 평균은 1,011.013ms에서 1,777.718ms로 증가했습니다. 호출 수는 같았고 DB mapping은 약 447ms로 비슷했습니다. 명시적인 종류 검사를 없앤 이득보다 파일 속성 조회 시간 증가가 컸습니다.

정확한 OS 또는 bind mount 내부 원인은 확인하지 않았습니다. `walk()`가 모든 환경에서 느리다는 결론이 아니라, **현재 환경·데이터·후속 stat 처리에서는 기존 구현이 유리하다**는 결과입니다.

검증: 관련 regression test 57개, `git diff --check`, 실제 API 응답 200 및 결과 수 일치. 결과: **미채택, 사용자 요청으로 d7fd8fb 코드 상태로 복원**.

## 5. 서버 재시작 직후와 Cache 재사용 비교

측정 시각은 한국 시간 2026-10-14 23:59~2026-10-15 00:00입니다. `d7fd8fb` 구현과 설정을 유지했습니다. 전체 조회와 작업별 조회가 서로 Cache를 채우지 않도록 각 조건마다 Docker Compose 서버를 별도로 재시작했습니다.

서버 준비 후 로그인하고 첫 페이지 목록과 24개 Thumbnail을 조회했습니다. 이후 10초 대기하고 같은 목록을 3회 재조회했습니다. 첫 재조회에서는 같은 Thumbnail 24개도 조회했습니다. 클라이언트는 서버 container 안의 `httpx`이며, 이 측정은 브라우저 화면 렌더링 시간이 아닙니다. OS·Docker의 filesystem Cache는 비우지 않았고 자동 Thumbnail Warmup은 그대로 실행했습니다. 처음 목록의 이미지 크기 Cache는 비어 있었으며 첫 Thumbnail은 모두 실제 miss였습니다.

| API 응답 완료 시간 | 전체 2,004개 | 작업 결과 70개 |
|---|---:|---:|
| 재시작 직후 첫 목록 | 2,383.974ms | 1,371.913ms |
| 첫 페이지·Thumbnail 조회 후 10초 대기한 첫 재조회 | 1,648.578ms | 657.151ms |
| 재조회 3회 범위 | 1,648.578~1,689.738ms | 657.151~693.512ms |
| 재조회 3회 평균 | 1,671.951ms | 674.494ms |

다음 표는 같은 API 요청의 서버 단계 누적 시간입니다. 첫 조회와 10초 대기 후 첫 재조회를 비교했으며 독립 탐색 실험의 시간과 섞지 않았습니다.

| 단계 | 전체 첫 조회 | 전체 재조회 | 작업 첫 조회 | 작업 재조회 |
|---|---:|---:|---:|---:|
| `DirEntry.is_file()` + 확장자 확인 | 2.618ms | 2.581ms | 4.036ms | 3.736ms |
| `Path.stat()` | 1,084.095ms | 1,065.665ms | 36.493ms | 38.827ms |
| 탐색 전체: 위 두 단계 포함 | 1,200.073ms | 1,191.768ms | 160.034ms | 152.154ms |
| DB mapping | 469.075ms | 452.302ms | 476.808ms | 456.027ms |
| 이미지 크기 확인: 24개 | 665.625ms | 0.145ms | 654.349ms | 0.162ms |

Thumbnail은 두 조건 모두 첫 조회 24개가 `miss`, 재조회 24개가 `hit`였습니다. 이미지 크기 Cache와 압축 Thumbnail Cache는 별개입니다. 목록 API의 속도 차이는 이미지 크기 읽기 약 0.65~0.67초가 사라진 영향이 컸습니다. 서버 재시작 직후에도 `DirEntry.is_file()`은 2,007회에 약 2.6~4.0ms였고, `stat()` 및 DB mapping은 재조회에서도 큰 비용이 남았습니다.

`is_dir()`은 탐색 helper에서 하위 폴더를 찾는 데 사용되며 현재 로그에서는 `directory_iteration` 안에 포함됩니다. `is_dir()`만의 시간은 이번 측정에서 별도로 분리하지 않았습니다.

원시 요청별 시간·호출 수·Cache 상태는 [재시작 비교 JSON](performance/output_restart_cache_2026-10-15.json)에 보관했습니다. 재현 스크립트는 ignored 파일인 `runtime/verification/output_restart_cache_check.py`입니다. 앱 구현은 수정하지 않았으며 최종 서버 상태는 healthy였습니다.

## 6. 파일명 metadata로 목록 stat 대체

2026-10-15 00:18~00:19에 적용 후 HTTP를 측정했습니다. 직전 재시작 비교의 `d7fd8fb` 표본을 baseline으로 사용했으며, 같은 2,004개 파일과 같은 작업 결과 70개를 조회했습니다. 두 조건의 첫 페이지 24개 파일과 순서도 같았습니다. 앱의 해상도 Cache와 Thumbnail Cache를 초기화하려고 전체·작업별 조회마다 서버를 재시작했고, 첫 목록·Thumbnail 조회 후 10초 대기한 재조회 3회 프로토콜을 그대로 사용했습니다. OS·Docker filesystem Cache는 비우지 않았고 자동 Warmup도 유지했습니다.

### 실제 생성 규칙 확인

- Anima: 앱의 `prepare_anima()`가 Saver에 `filename=%time_%seed`, `time_format=%y%m%d_%H%M%S`를 지정합니다. 현재 사용자가 수정한 Workflow template의 다른 초기 값도 요청 준비 때 이 값으로 바뀝니다. Template 자체는 이번 작업에서 수정하지 않았습니다.
- MiniMax: `filename_prefix=%date:yyMMdd_HHmmss%_%seed%`이며 sampling seed를 Saver에 연결합니다. Saver가 붙이는 counter 및 `_audio` suffix도 파일명 parser에서 허용합니다.
- 설치된 `comfyui-image-saver/nodes.py`와 `ComfyUI-DaSiWa-Nodes/nodes/nodes_enhanced_video_combine.py`를 직접 확인했습니다. Anima 시각은 Saver의 파일명 생성 시각이며 MiniMax 시각은 encoding 전에 확정됩니다. 파일 수정 시각·encoding 완료 시각과 같은 값이라고 가정하지 않습니다.
- 실제 결과물 2,004개의 이름이 모두 `yyMMdd_HHmmss_seed` 형식으로 시작했습니다. 예: `261010_194351_1898263605.png`.
- Seed는 현재 요청마다 `randbelow(2**31)`로 뽑는 랜덤값입니다. Unique나 같은 초 안의 시간 순서를 보장하지 않으므로 마지막 tie-breaker는 전체 경로입니다.

### 구현 범위와 동작 변화

- `scandir()`, `DirEntry.is_file()`, 탐색 helper의 `is_dir()`, 전체 탐색 후 작업 필터는 유지했습니다.
- 목록의 파일별 `Path.stat()`을 없애고 파일명 parsing을 `filename_metadata`로 측정합니다.
- 정렬은 파일명 시각 → 숫자 seed → 경로 내림차순입니다. 지원하지 않는 이름이나 잘못된 날짜는 시각·seed를 `null`로 반환하고 목록 끝에 표시합니다. `stat()` fallback은 없습니다.
- 목록 API의 `size`·`modified_at`을 제거하고 `generated_at`·`seed`를 반환합니다. 화면의 MB 표시는 제거했습니다.
- 실제 해상도 읽기는 유지했습니다. 기존 `mtime_ns + size` Cache key를 쓰지 않으므로 경로 기준 최대 2,048개, 60초 TTL Cache로 변경했습니다. 같은 경로 덮어쓰기는 최대 60초 뒤 해상도에 반영되며 앱의 파일 이동은 관련 Cache를 즉시 무효화합니다.
- 썸네일·원본 접근에서 파일 존재·속성·경로를 확인하는 기존 동작은 유지했습니다. 전체 FS 작업이나 모든 API의 `stat()`을 없앤 변경은 아닙니다.

## 7. 해상도 Cache TTL 제거

사용자는 파일명을 재사용해 덮어쓸 일이 거의 없으므로 60초 TTL을 매우 길게 늘리거나 제거하도록 요청했습니다. 시간 만료 자체를 제거하고 경로별 해상도만 최대 2,048개 LRU로 보관하도록 단순화했습니다. Cache miss일 때 실제 이미지 header를 읽고, hit에서는 clock이나 filesystem metadata를 확인하지 않습니다.

같은 경로의 덮어쓰기는 자동으로 감지하지 않으며 해당 항목의 LRU 퇴출·명시적 무효화·서버 재시작 후 다시 읽습니다. 앱에서 파일을 이동할 때의 경로별 무효화는 유지했습니다. Thumbnail Cache의 수정 시각·크기 key 및 파일 접근 확인은 이번 변경 대상이 아닙니다.

6번의 측정값과 원시 JSON은 당시 60초 TTL 버전의 기록으로 보존했습니다. 이번 요청에서는 성능 재측정을 하지 않았으며 관련 regression test로 Cache 재사용·명시적 무효화·LRU 개수 제한을 확인했습니다. 결과는 10 passed, 1 skipped(Windows Symlink 권한)입니다.

## 8. 해상도 Cache 최대 항목 수 확대

사용자 요청으로 최대 항목 수를 2,048개에서 30,000개로 늘렸습니다. TTL 없이 경로별 해상도를 재사용하고, 개수 초과 시 LRU 퇴출 및 앱의 파일 이동 시 무효화하는 동작은 유지합니다. 기존 성능 측정은 당시의 최대 항목 수 기준 기록으로 보존합니다.

## 남은 논의와 실험 기준

- 썸네일·원본 접근의 `stat()`이 필요한 정보와 중복 조회 여부: 목록과는 별도 범위입니다.
- 작업에 기록된 path만 직접 조회하는 방식: 아직 제안 단계이며 이번 실험들의 채택 결과에 포함하지 않습니다.
- 현재 약 0.45초인 DB output mapping: 측정 당시 `EXPLAIN QUERY PLAN`에서 전체 요청 및 JSON output path 탐색이 확인됐습니다. 아직 최적화하지 않았습니다.
- 목록 index 또는 Cache 도입: 아직 구현하지 않았습니다.
- 개별 실험은 baseline commit, 변경 내용, 환경·데이터 수, 반환 결과 일치, 브라우저와 내부 측정 범위, 반복 표본, 채택 여부를 함께 남깁니다.

상세한 로컬 보고서·snapshot·재현 스크립트는 `runtime/verification/`에 남겼습니다. 해당 파일은 ignored이므로 저장소 문서의 JSON 기록에 주요 측정 데이터를 함께 보관했습니다.

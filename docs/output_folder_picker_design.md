# 결과물 폴더 탐색기 설계

작성일: 2026-10-19

상태: **폴더 탐색·새 폴더 생성·세 이동 UI 연동을 구현했습니다.** 설계 문서를 `42bcb4e`로 먼저 커밋한 뒤 구현했습니다. MiniMax 연동과 폴더 삭제는 후속 범위로 유지합니다.

설계 당시 구현 기준 Commit: `ceaa734` (`feat: support job-wide and selected output folder moves`). 2장의 현재 동작 설명은 이 기준의 재사용 지점을 기록합니다.

## 1. 사용자와 합의한 범위

현재 이동 목적지를 `window.prompt()`로 직접 입력하는 방식을 서버의 폴더를 탐색하여 선택하는 UI로 바꿉니다.

- 탐색기의 유일한 루트는 **현재 관리 중인 결과물 폴더**입니다.
- PC 전체 드라이브나 다른 서버 폴더를 탐색하지 않습니다.
- 루트보다 상위로 이동할 수 없습니다.
- 이동 목적지를 고르다가 **새 폴더를 생성**할 수 있어야 합니다.
- 단건 이동, 결과물 다중 이동, 작업 전체 결과물 이동에서 같은 탐색기를 재사용합니다.
- 향후 MiniMax의 서버 이미지·폴더 선택에도 같은 탐색기 기반을 사용합니다. **MiniMax 연동 자체는 이번 구현 범위가 아닙니다.**
- **폴더 삭제는 구현하지 않습니다.** 폴더 안 결과물의 생성 이력과 DB 상태를 함께 고려해야 하므로 별도 후속 설계로 남깁니다.
- 현재 이미 구현된 단건·다중 이미지 삭제는 유지합니다. 폴더 삭제의 보류와 기존 이미지 삭제 기능은 구분합니다.

## 2. 현재 구현과 재사용 지점

| 파일 | 현재 동작과 연결 지점 |
|---|---|
| `home_server/configuration.py` | `AppConfig.managed_output_directory`가 관리 결과물 루트입니다. |
| `compose.yaml` | `${COMFY_MANAGED_OUTPUT_DIRECTORY}`를 `/comfy-output/from_home_server`에 Mount합니다. 추가 Mount는 필요하지 않습니다. |
| `home_server/application.py` | `HomeServer.managed_path()`가 관리 폴더 경계를 검증합니다. `move_managed_output()`·`move_recorded_outputs()`가 공통 이동 처리를 담당합니다. |
| `home_server/output_catalog.py` | `output_files.relative_path`에 현재 상대 경로가 있습니다. `move_file()`은 현재 경로만 갱신하고 작업·요청 연결을 보존합니다. |
| `web/app.js` | `moveOutput()`·`moveSelectedOutputs()`·`moveJobOutputs()`가 각각 목적지 입력에 `window.prompt()`를 사용합니다. 이 입력 부분을 공용 Picker로 교체합니다. |
| `web/index.html`·`web/app.css` | 공용 Dialog와 모바일 탐색 UI를 추가할 위치입니다. |
| `tests/test_output_movement.py` | 작업·다중 이동, 충돌, 동일 목적지, 실패 시 경로 보존에 대한 기존 검증입니다. |
| `tests/browser_output_deletion.cjs` | Desktop·Mobile의 이동·삭제·선택·부분 실패·재시도를 함께 검증합니다. |

기존 이동 API:

| 동작 | API | 요청 |
|---|---|---|
| 단건 이동 | `POST /api/outputs/move` | `source`, `destination_folder` |
| 선택 결과물 이동 | `POST /api/outputs/move-batch` | `output_ids`, `destination_folder` |
| 작업 전체 이동 | `POST /api/jobs/{job_id}/outputs/move` | `destination_folder` |

이미 구현된 정책도 유지합니다.

- 작업 전체 이동은 생성이 끝난 작업에서만 허용합니다.
- 작업 이동은 모든 페이지의 사용 가능한 결과물을 현재 경로에서 이동합니다.
- 삭제 보호된 결과물과 영상도 이동할 수 있습니다. 삭제 보호는 삭제에 적용합니다.
- 목적지에 같은 이름의 파일이 있으면 덮어쓰지 않고 해당 항목의 실패를 반환합니다.
- 이미 같은 폴더에 있는 파일은 건너뜁니다.
- 다중 이동은 성공·건너뛰기·실패를 구분하고, 실패한 선택 항목은 재시도할 수 있도록 유지합니다.
- 이동 중 선택과 다른 파일 조작을 잠그는 기존 UI 동작을 유지합니다.

## 3. 경로 규약

PC와 Docker의 절대 경로가 같아지는 것은 아닙니다. **같은 물리적 폴더를 루트로 삼고, 그 아래 상대 경로를 통일합니다.**

| 사용 위치 | 예시 |
|---|---|
| PC | 설정된 `managed_output_directory` + `anima/example.png` |
| Docker | `/comfy-output/from_home_server/anima/example.png` |
| DB `relative_path` | `anima/example.png` |
| Picker의 파일 참조 | `anima/example.png` 또는 기존 `output_id` |
| Picker의 폴더 선택 결과 | `anima` 또는 `sorted/favorites` |

- 프런트엔드와 DB의 상대 경로 구분자는 `/`로 통일합니다.
- 프런트엔드에 Windows나 Docker의 절대 경로를 전달하지 않습니다.
- 루트가 하나이므로 여러 Root를 구분하는 `root_id`나 새로운 경로 매핑 설정은 필요하지 않습니다.
- 파일 작업의 현재 위치는 `output_files.relative_path`를 기준으로 합니다.
- `original_relative_path`와 `request_results.result_json.output_paths`는 생성 당시 경로입니다. 현재 위치를 찾는 기준으로 사용하거나 Picker 도입 때문에 덮어쓰지 않습니다.

### 루트 표현 제안

API와 Picker 내부에서는 빈 문자열 `""`을 루트로 사용하고, 화면에서는 `결과물` 또는 `/`로 표시합니다. 하위 폴더는 앞뒤 `/`가 없는 상대 경로로 표현합니다.

**현재 코드에서 별도로 해결해야 하는 부분:**

- `managed_path()`는 현재 빈 문자열과 루트 자신을 거부합니다.
- `MoveDestinationInput.destination_folder`는 현재 `min_length=1`입니다.
- 따라서 루트 조회·루트 아래 새 폴더 생성·루트로 이동을 지원하려면 목적에 맞는 루트 허용 처리가 필요합니다.
- 루트 허용은 폴더 조회·폴더 생성의 부모·이동 목적지에 한정합니다. 파일 원본 경로를 루트로 허용하거나 기존 파일 경계 검증을 일괄 완화하지 않습니다.
- 공용 폴더 경로 Resolver를 만들거나 명시적인 `allow_root` 옵션을 두는 방식을 검토합니다.

## 4. 폴더 목록과 파일 목록의 데이터 원천

### 폴더 목록: FS에서 해당 폴더의 직계 하위만 조회

`output_files`는 파일 Catalog이므로 빈 폴더를 표현하지 않습니다. DB 경로에서 폴더 이름만 추출하면 새로 만든 빈 폴더가 보이지 않습니다.

- 폴더를 열 때 그 폴더의 **직계 하위 폴더만** `scandir()` 등으로 조회합니다.
- 전체 디렉터리를 재귀 탐색하여 Tree 전체를 한 번에 만들지 않습니다.
- 이미지 내용·해상도를 읽거나 하위 폴더의 전체 파일 개수를 계산하지 않습니다.
- 새 폴더도 FS 조회 결과에 즉시 나타나야 합니다.
- 폴더 전용 DB 테이블과 schema Migration은 필요하지 않습니다.
- 기존 결과물 목록의 DB 기반 조회·정렬·Pagination을 FS 전체 탐색으로 바꾸지 않습니다.

### 파일 목록: 향후 MiniMax 모드에서 기존 Catalog 활용

- 현재 경로인 `relative_path`와 파일 식별자인 `output_id`를 사용합니다.
- `is_available=1`, `is_deleted=0`인 이미지가 대상입니다.
- 폴더 필터는 경로 구분자 경계를 지켜야 합니다. `anima`와 `anima-other`를 같은 폴더로 취급하지 않습니다.
- 직계 파일 조회와 하위 폴더 포함 조회는 명시적으로 구분합니다.
- 기존 Thumbnail 생성 로직을 재사용할 수 있습니다.
- 외부 파일의 Catalog 등록은 기존 서버 시작·수동 Sync 정책과 구분합니다. Picker에서 폴더를 열 때마다 전체 Sync를 실행하지 않습니다.

## 5. 공용 Picker UI

현재 Vanilla JavaScript와 기존 스타일을 유지하면서 작은 공용 Component로 구현하는 방향을 권장합니다. 외부 File Manager 라이브러리 도입은 필수 조건이 아닙니다.

이번 단계의 모드는 **이동 목적지 폴더 하나 선택**입니다.

필요한 조작:

- 현재 위치를 표시하는 Breadcrumb
- 상위 폴더로 이동: 루트에서는 비활성화하거나 숨김
- 하위 폴더 목록과 폴더 열기
- `새 폴더` 버튼과 폴더 이름 입력
- `이 폴더로 이동` 또는 같은 의미의 선택 완료 버튼
- 취소
- 목록 Loading·빈 폴더·조회 실패 표시와 재시도

모바일에서는 터치하기 쉬운 항목과 버튼을 사용하고, 좁은 화면에서 가로 Scroll이 생기지 않게 합니다. Desktop의 복잡한 다중 Panel 탐색기를 전제로 하지 않습니다.

선택 완료 시 기존 이동 함수에 상대 폴더 경로를 반환합니다. Picker 자체가 별도의 파일 이동 로직을 갖지 않고, 현재 API의 DB 갱신·충돌·부분 실패 처리를 재사용합니다.

## 6. 새 폴더 생성

사용자가 요구한 필수 기능입니다. 다음은 구체적인 구현 동작 제안입니다.

1. 현재 열려 있는 폴더에서 `새 폴더`를 누릅니다.
2. 새 폴더 이름 한 개를 입력합니다.
3. 서버가 부모 경로와 이름을 검증한 뒤 직계 하위 폴더 하나를 생성합니다.
4. 목록을 갱신하고 생성한 폴더를 열거나 선택할 수 있게 합니다.
5. 사용자가 목적지를 확정하면 기존 이동 API를 호출합니다. 폴더 생성만으로 파일 이동을 시작하지 않습니다.

생성 정책 제안:

- 부모는 이미 존재하는 관리 루트 또는 그 하위 Directory여야 합니다.
- 이름에 `/`·`\`를 넣어 여러 단계 경로를 한 번에 생성하지 않습니다.
- 빈 이름, `.`·`..`, 절대 경로, 제어 문자, Windows에서 사용할 수 없는 문자·예약 이름·끝의 공백 또는 마침표를 검증합니다. Docker에서 생성한 폴더가 Windows에서도 정상 접근되어야 합니다.
- 이름 중복이나 같은 이름의 파일이 있으면 실패를 알리고 기존 항목을 그대로 둡니다.
- 생성 시점의 충돌도 처리합니다. 클라이언트의 사전 확인만으로 판단하지 않습니다.
- 권한 부족·부모 폴더 소멸 등 실패를 표시하고 사용자가 다른 이름이나 위치로 재시도할 수 있게 합니다.
- 빈 폴더 생성은 FS 변경만 수행합니다. `output_files`에 가짜 파일 행을 추가하거나 작업·요청 JSON을 변경하지 않습니다.
- 폴더 생성 후 이동을 취소하면 이미 생성한 빈 폴더는 남겨 두는 동작을 권장합니다. 취소 과정에서 폴더를 자동 삭제하지 않습니다.

## 7. 추가 API

아래 API를 구현했습니다. 폴더 생성 성공은 HTTP 201, 입력 오류는 422, 없는 폴더는 404, 이름 충돌은 409, 접근 권한 등 FS 오류는 403으로 반환합니다.

### 폴더 조회

`GET /api/outputs/directories?path=sorted`

```json
{
  "path": "sorted",
  "parent_path": "",
  "directories": [
    {"name": "favorites", "path": "sorted/favorites"}
  ]
}
```

루트 조회는 `path=`이며 `parent_path`는 `null`로 반환하는 방안을 권장합니다.

### 새 폴더 생성

`POST /api/outputs/directories`

```json
{
  "parent_path": "sorted",
  "name": "favorites"
}
```

성공 응답에는 생성한 폴더의 `name`과 `path`를 반환합니다. 입력 오류·존재하지 않는 부모·중복·권한 오류를 구분합니다.

두 API 모두 기존 인증을 적용합니다. 클라이언트가 임의 요청을 보내더라도 루트 밖에 접근할 수 없도록 서버에서 경계를 검증합니다. `..`, 절대 경로, symlink·Windows Junction 등으로 루트를 벗어나는 접근을 차단하고, 조회와 생성에 같은 경계 정책을 적용합니다.

## 8. 향후 MiniMax 재사용 범위

현재 `web/index.html`의 `minimax-images`·`minimax-directory`는 `<input type="file">` 및 `webkitdirectory`를 사용하므로 **접속 단말의 파일 선택기**가 열립니다.

후속 작업에서는 같은 결과물 루트의 서버 파일을 선택하는 모드를 추가합니다.

| 모드 | 선택 대상 |
|---|---|
| 이번 이동 목적지 | 폴더 하나 |
| 향후 MiniMax 이미지 입력 | 이미지 한 장 또는 여러 장 |
| 향후 MiniMax 폴더 입력 | 폴더와 그 안의 대상 이미지 목록 |

- 별도 서버 폴더나 추가 Mount를 도입하지 않습니다.
- Browser는 선택한 결과물의 ID 또는 관리 상대 경로를 전달합니다. 휴대폰으로 이미지를 다운로드한 뒤 다시 업로드하지 않습니다.
- 서버에서 선택 이미지를 임시 입력으로 복사하여 기존 `upload_id` 흐름에 연결하는 방식을 우선 검토할 수 있습니다. 원본 결과물은 보존합니다.
- 현재 MiniMax 입력 처리는 임시 업로드 파일을 찾아 ComfyUI `/upload/image`로 전달합니다. 서버 결과물 선택 후에도 이 처리 경로를 재사용할 수 있습니다.
- 폴더 선택 시 하위 폴더 포함 여부, 파일 순서, 이미지 개수 확인, 현재 Batch 최대 100장 제한의 적용은 후속 구현에서 정리합니다.
- 결과물 삭제 보호는 입력 이미지로 읽는 것을 막는 설정이 아닙니다.
- 삭제·이동 등으로 선택 이후 원본이 바뀐 경우에는 ID로 현재 경로를 다시 확인하고 파일 존재를 검증해야 합니다.

## 9. 명시적인 제외 범위

- 폴더 삭제와 재귀 삭제 API·버튼
- 폴더 삭제에 따른 결과물 Tombstone·생성 이력 변경 정책
- 폴더 이름 변경, 폴더 전체 이동, 복사, 압축 등 범용 File Manager 기능
- PC 전체 드라이브·Mount되지 않은 폴더 탐색
- 추가 Mount 및 여러 Root를 지원하는 구조
- 이번 단계에서의 MiniMax 입력 변경
- 폴더 전용 DB schema, 전체 디렉터리 사전 Index 및 재귀 Scan
- 기존 이미지 삭제·작업 이력 삭제 정책의 변경

폴더 삭제를 추후 구현할 때는 폴더 안 파일과 `output_files`의 현재 경로·삭제 플래그, 생성 당시 JSON, 작업·요청 연결, 삭제 보호와 부분 실패를 함께 검토해야 합니다. 폴더를 FS에서 먼저 지우는 기능만 추가하지 않습니다.

## 11. 구현 기록

- `home_server/output_directories.py`: 폴더 전용 경계 검증, 직하위 폴더 조회, 단일 폴더 생성입니다. 파일 원본 경로 검증인 `managed_path()`는 완화하지 않았습니다.
- `resolve_output_directory()`는 빈 문자열만 루트로 허용하며 절대·상위 경로와 내부/외부 symlink·Windows junction을 거부합니다. 조회에서는 링크를 숨깁니다. 폴더 목록은 `os.scandir()`로 확인하며 이미지 파일을 열거나 하위 트리를 재귀 탐색하지 않습니다.
- 새 폴더 이름은 단일 구성요소로 검증하며 Windows 금지 문자·예약 장치 이름·제어 문자·끝의 점/공백을 거부합니다. 부모를 확인한 뒤 `mkdir(exist_ok=False)`로 생성하여 중복 경합에서도 기존 폴더나 파일을 덮어쓰지 않습니다.
- 기존 이동 API는 폴더 전용 검증으로 루트 목적지를 지원합니다. 기존 API의 없는 목적지 자동 생성 동작은 호환성을 위해 유지하되, UI는 탐색하거나 명시적으로 생성한 폴더를 선택합니다.
- `chooseOutputFolder()`는 native `dialog` 기반 공용 UI입니다. 취소는 `null`, 루트 선택은 `""`로 구분합니다. 새 폴더 생성 중에는 중복 조작·취소를 막고, 완료 후 새 폴더를 엽니다. 로그인 만료 시 창을 닫으며, 닫거나 다시 연 창에 이전 응답을 반영하지 않습니다.
- `tests/test_output_directories.py`: 인증, 빈/중첩 폴더, 이름/경로 오류, 중복/경합/권한 오류, 실제 symlink 또는 Windows junction, 세 이동 방식의 루트 복귀, DB/JSON 보존을 검증합니다.
- `tests/browser_output_deletion.cjs`: Desktop/Mobile의 공용 탐색, 세 이동 방식, 폴더 생성 후 취소, 루트 이동, Breadcrumb, 조회 실패 재시도, 늦은 응답, Keyboard 취소, 긴 이름의 가로 Overflow를 검증합니다. 운영 결과물 대신 Mock API를 사용합니다.

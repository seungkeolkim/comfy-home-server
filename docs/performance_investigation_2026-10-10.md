## 탭 구분과 확인 범위

아래에서는 PC의 실제 메뉴 이름을 기준으로 **생성**, **작업**, **결과물**, **태그 관리** 탭을 구분합니다. 모바일의 `태그`는 PC의 `태그 관리`와 같은 화면입니다. 사용자가 말씀하신 작업 이력은 **작업 탭**에 있습니다.

HTTP 및 서버 내부 측정은 Browser에서 해당 탭을 클릭하며 잰 시간이 아니라, 같은 API나 내부 처리를 직접 호출하여 잰 시간입니다. 표의 **관련 탭**은 그 기능을 사용하는 화면을 뜻합니다. 실제 화면 증상은 Mock Browser 재현 결과에 별도로 표시합니다.

| 관련 탭 | 증상 또는 점검 대상 | 확인 수준 |
| --- | --- | --- |
| 작업 | 이력·결과물 함께 삭제할 때 지연 | 사용자 보고, 동기 파일 삭제 구조 확인. 실제 삭제 시간은 미측정 |
| 작업 | 작업이 남아 있는데 빈 목록으로 표시 | 느린 Polling 및 삭제 직후 흐름에서 Mock Browser로 재현 |
| 작업 | 무거운 이력 응답과 반복 렌더링 | 실제 API 응답 크기 측정, 코드 확인 |
| 결과물 | 결과물 목록 조회 지연 | 실제 API 및 서버 내부 처리 시간 측정 |
| 생성 | 태그 참조 탐색·선택 UI 렌더링 비용 | Edge Desktop에서 분리 측정. 큰 병목은 확인되지 않음 |
| 태그 관리 | 태그 관리 UI 렌더링 비용 | Edge Desktop에서 분리 측정. 큰 병목은 확인되지 않음 |
| 공통: 모든 탭 | 백그라운드 작업 조회, 초기 결과물 조회, 서버 요청 간 지연 전파 | 코드 확인 및 실제 동시 HTTP 요청 측정 |

태그가 늘어난 뒤 전체 반응이 느리다는 사용자 보고만으로는 특정 탭의 태그 기능이 원인이라고 단정할 수 없습니다. 현재 측정에서는 동기 I/O, 무거운 작업 이력 응답, 중복 Polling이 우선 개선 대상으로 확인되었습니다. **Prompt·LoRA 조합 탭은 별도의 성능 측정을 하지 않았습니다.**

## 작업 탭

### 1. 매초 Polling이 느린 응답을 계속 폐기할 수 있습니다

[`web/app.js`](../web/app.js)의 `showApplication()`은 `setInterval(loadJobs, 1000)`으로 매초 작업 이력을 조회합니다. 진행 중인 작업이 없거나 다른 탭을 보고 있어도 Polling을 계속합니다.

`loadJobs()`는 요청을 시작할 때마다 `jobsLoadRevision`을 증가시키고, 응답이 도착했을 때 최신 Revision과 다르면 응답을 버립니다. 이전 요청이 끝나기 전에 다음 Polling을 시작하는 것을 막는 처리가 없어, 응답이 1초 이상 걸리는 동안에는 유효한 응답도 계속 폐기될 수 있습니다.

#### 작업 탭의 느린 Polling 재현

분리된 Browser에서 실제 데이터 규모의 작업 이력 응답을 사용하고, Mock API 응답을 1,500 ms 지연시켰습니다.

- API는 작업 10개가 담긴 응답을 4회 완료했습니다.
- 화면의 작업 수는 0개로 유지되었고 `제출한 작업이 없습니다.`가 표시되었습니다.
- 중복 Polling을 멈추고 마지막 응답을 기다리자 작업 10개가 정상 표시되었습니다.

#### 작업 탭에서 삭제 직후 빈 목록 재현

Mock API에서 현재 페이지의 작업 10개를 선택하여 `선택된 이력·결과물 삭제` 흐름을 실행했습니다. 삭제는 메모리의 Mock 목록에만 적용했습니다.

- Mock 서버에는 삭제 후에도 작업 25개가 남아 있었습니다.
- `deleteSelectedJobHistory()`가 삭제한 작업을 `visibleJobs`에서 제거한 뒤, 느린 재조회와 Polling이 겹쳤습니다.
- 서버에 작업이 남아 있는데 화면에는 0개와 `제출한 작업이 없습니다.`가 표시되었습니다.
- Polling을 멈추자 다음 페이지로 채워질 작업 10개가 정상 표시되었습니다.

이 재현은 실제 데이터 소실이 아니라 화면 갱신 실패입니다. 개별 현장의 모든 빈 목록 표시가 같은 원인이라고 단정하지는 않지만, 사용자가 설명한 증상을 현재 코드로 재현할 수 있습니다.

### 2. 이력·결과물 함께 삭제할 때 동기 파일 처리를 수행합니다

여기서 **이력·결과물 삭제 버튼은 작업 탭에 있는 버튼**입니다. 결과물 탭의 목록 조회와는 다른 동작입니다. [`home_server/application.py`](../home_server/application.py)의 `delete_job()`은 `async def`이지만 파일 삭제를 동기적으로 수행하여, 처리 중 같은 서버의 Event loop가 다른 요청을 처리하지 못할 수 있습니다.

[`home_server/database.py`](../home_server/database.py)의 `delete_job()`은 `BEGIN IMMEDIATE` 후 삭제 보호와 활성 상태를 검사하고, 파일 삭제 Callback을 실행한 뒤 이력을 삭제합니다. 따라서 파일 처리 시간만큼 DB의 쓰기 잠금도 유지됩니다. 이 잠금 자체가 모든 읽기 요청을 막는다는 의미는 아니지만, 다른 쓰기 작업의 대기 원인이 될 수 있습니다.

실제 사용자의 작업이나 결과물을 삭제하는 성능 측정은 하지 않았습니다. **삭제가 실제로 몇 ms 걸리는지는 확인되지 않았습니다.** 파일 포함 삭제의 구조적 병목은 코드에서 확인했고, 삭제 후 화면 갱신 문제는 앞 절의 분리된 Mock API로 재현했습니다.

### 3. 작업 이력 응답에 후보 Snapshot이 반복 포함됩니다

[`home_server/database.py`](../home_server/database.py)의 `list_jobs()`는 한 페이지의 모든 하위 요청과 `detail_json`을 읽어 반환합니다. 생성 화면 복원을 위해 저장한 `selected_tags` 후보 Snapshot도 각 하위 요청에 포함됩니다.

| 관련 탭 | 측정 항목 | 결과 |
| --- | --- | --- |
| 작업 / 태그 관리 (데이터 규모) | 최초 점검 시 데이터 규모 | 작업 30개, 하위 요청 114개, 태그 그룹 20개, 태그 항목 127개 |
| 작업 | 작업 10개를 반환하는 실제 API 응답 | 약 434 ~ 633 KB |
| 작업 | 분리 측정한 작업 이력 JSON 크기 | 666,855 bytes |
| 작업 (생성 탭 복원용 데이터 포함) | 위 JSON의 후보 Snapshot 부분 | 565,060 bytes, 약 85% |
| 작업 (생성 탭 복원용 데이터 포함) | 최신 요청 후보 Snapshot 예시 | 선택 후보 70개, 약 25 KB |

점검 중 사용자가 작업을 계속 생성·삭제했으므로 측정 시점마다 작업 수와 응답 크기가 달랐습니다. Python으로 직렬화한 분리 측정 JSON과 실제 API JSON은 직렬화 형식도 달라 크기가 완전히 같지는 않습니다.

현재 Browser는 이 응답을 매초 받고, 변경 여부와 무관하게 `renderJobsList()`에서 작업 카드와 접힌 하위 요청의 HTML까지 다시 만듭니다. 로컬에서는 처리할 수 있는 크기여도 모바일이나 느린 연결에서는 전송·JSON parsing·DOM 갱신 부담이 커질 수 있습니다.

후보 Snapshot을 보관하는 기능 자체는 필요합니다. 병목의 핵심은 복원에 필요한 전체 데이터를 상태 갱신용 Polling에서도 반복 전송한다는 점입니다.

Snapshot은 생성 탭에서 복원할 때 쓰이지만, 위 표의 큰 응답은 **작업 목록 조회 API**에서 측정한 것입니다. 생성 탭 복원 버튼을 누르는 데 걸리는 시간을 측정한 결과가 아닙니다. 다른 탭을 보고 있어도 동일한 작업 목록 Polling은 계속 실행됩니다.

### 4. 작업 카드 렌더링 자체의 분리 측정

| 관련 탭 | Browser 처리 | 측정 범위 |
| --- | --- | --- |
| 작업 | 작업 카드 렌더링, 5회 | 1.3 ~ 1.6 ms |

실제 작업 데이터를 사용한 Edge Desktop 측정입니다. API 대기·응답 전송을 포함하지 않습니다. 카드 HTML을 만드는 비용이 작더라도 매초 큰 응답을 받고 반복 갱신하는 비용은 별도로 고려해야 합니다.

## 결과물 탭

### 1. 결과물 목록 API의 응답이 1초 이상 걸렸습니다

| 관련 탭 | 측정 항목 | 소요 시간 |
| --- | --- | --- |
| 결과물 | 결과물 목록 API 조회, 3회 | 1,140.6 / 1,262.3 / 1,264.2 ms |

위 시간은 목록 API의 응답 시간입니다. Browser의 미리보기 이미지 다운로드·화면 표시 완료까지 포함한 시간은 아닙니다. 결과물 탭 진입 및 페이지 변경 시 같은 목록 API를 호출합니다. 초기 앱 로딩에서도 호출되므로 결과물 탭을 열지 않아도 이 비용이 발생할 수 있습니다.

### 2. 결과물 페이지를 조회할 때 전체 폴더와 이미지 크기를 다시 읽습니다

`outputs()`는 매번 관리 폴더 전체를 `rglob()`으로 탐색하고 각 파일의 경로·수정 시간 등을 확인합니다. 이후 선택한 페이지의 이미지 크기를 다시 읽고, `find_output_requests()`에서 SQLite JSON을 조회하여 작업 이력을 연결합니다.

컨테이너 안에서 이 처리를 나누어 측정한 결과입니다.

| 관련 탭 | 처리 | 소요 시간 |
| --- | --- | --- |
| 결과물 | 전체 파일 정보 확인, 파일 126개 | 521.5 ms |
| 결과물 (목록에 작업 연결 정보 표시) | 결과물과 작업 이력 연결 조회 | 119.9 ms |
| 결과물 | 한 페이지의 이미지 24개 크기 읽기 | 741.7 ms |

분리 측정 결과이므로 앞의 HTTP 측정과 정확히 같은 요청의 단계별 시간은 아닙니다. 다만 파일 수가 많지 않은 상태에서도 Windows bind mount를 통한 파일 확인·읽기 비용이 상당하다는 것을 보여 줍니다.

작업 이력 연결 조회는 결과물 카드의 `작업` 버튼 등에 필요한 정보를 찾는 과정입니다. 위의 119.9 ms는 작업 탭 목록을 조회한 시간이 아닙니다.

## 생성 탭

현재 태그 데이터를 분리된 Edge Desktop Browser에 넣고 각 처리를 5회 측정했습니다.

| 관련 탭 | Browser 처리 | 측정 범위 |
| --- | --- | --- |
| 생성 | 필요한 태그 참조 탐색 | 0 ~ 0.2 ms |
| 생성 | 태그 선택 UI 렌더링 | 0.9 ~ 1.4 ms |

## 공통: 여러 탭에 영향을 줄 수 있는 처리

### 1. 결과물 조회가 작업 이력 등 다른 요청까지 지연시킵니다

`outputs()`는 `async def`로 정의되어 있지만, 파일 탐색·경로 확인·파일 정보 읽기·이미지 크기 읽기를 동기적으로 수행합니다. 이 처리 중에는 같은 서버의 Event loop가 다른 요청을 처리하지 못할 수 있습니다.

| 관련 탭 | 측정 항목 | 소요 시간 |
| --- | --- | --- |
| 공통 (특정 탭 없음: 로그인 상태 확인) | 평상시 Session 조회 | 수 ms ~ 20 ms 수준 |
| 공통 (특정 탭 없음: 로그인 상태 확인) | 결과물 조회와 동시에 보낸 Session 조회 | 1,266.8 ms |
| 작업 (결과물 조회의 영향을 받는 요청) | 결과물 조회와 동시에 보낸 작업 이력 조회 | 1,278.9 ms |

동시 요청 검사에서는 결과물 조회를 시작하고 약 150 ms 뒤 Session·작업 이력 요청을 보냈습니다. 가벼운 Session 요청도 함께 지연되어, **결과물 조회 중 다른 HTTP 요청도 지연되는 현상**을 확인했습니다. 이 검사는 실제 HTTP 요청 측정이며, 사용자가 특정 탭을 클릭했을 때의 체감 시간을 측정한 것은 아닙니다.

다른 탭의 서버 요청에도 영향을 줄 수 있는 구조지만, 모든 탭의 모든 동작에서 지연을 실측한 것은 아닙니다. Browser 내부에서만 처리되는 입력이나 렌더링까지 서버 Event loop가 직접 멈춘다는 의미도 아닙니다.

### 2. 탭을 열지 않아도 목록 조회가 실행됩니다

- 로그인 직후 `showApplication()`은 현재 보이는 탭과 관계없이 작업·결과물 목록 등을 함께 조회합니다.
- 이후 작업 목록은 진행 중인 작업 유무나 현재 탭과 관계없이 매초 Polling합니다.
- 결과물 목록은 매초 Polling하지 않습니다. 초기 앱 로딩, 결과물 탭 진입, 페이지 이동·필터 변경 등의 동작으로 조회됩니다.

따라서 생성·태그 관리·Prompt·LoRA 조합 탭을 보고 있을 때 발생한 서버 지연도 백그라운드 작업 조회나 초기 결과물 조회와 관련될 수 있습니다. 이 항목은 코드로 확인한 실행 조건이며, 각 탭에서 동일한 지연을 개별 재현했다는 뜻은 아닙니다.

### 3. Browser 렌더링 측정의 해석 범위

모든 Browser 처리 시간은 Edge Desktop 환경의 측정값입니다. API 대기·응답 전송을 포함하지 않으며, 모바일에서도 같은 시간이 나온다고 보장하지 않습니다. 현재 측정에서는 태그 개수를 줄이는 것보다 서버 I/O와 Polling 구조를 먼저 개선하는 것이 우선입니다.

## 개선 우선순위

1. **중복 Polling과 잘못된 빈 목록 표시부터 수정합니다.** 이전 조회가 끝나기 전에 다음 조회를 시작하지 않도록 하고, 재조회 중에는 기존 목록과 Loading 상태를 유지합니다. 초기 로딩·갱신 중·정상적인 빈 목록·조회 오류를 구분합니다. 진행 중인 작업이나 현재 화면에 맞춰 Polling 여부도 조절합니다.
2. **파일 조회·삭제를 별도 Thread에서 처리합니다.** 동기 I/O가 서버의 Event loop를 막지 않도록 옮깁니다. 삭제 보호의 DB 재검사와 파일 처리 중 보호 변경 차단은 유지해야 합니다.
3. **작업 상태 조회와 상세·복원 데이터 조회를 분리합니다.** Polling에는 상태와 요약만 보내고, 하위 요청 세부나 생성 탭 복원을 요청할 때 전체 Snapshot을 조회합니다. 기존 후보 Snapshot은 유지합니다.
4. **이미지 크기 정보를 재사용합니다.** 파일 경로·수정 시간·크기 등을 기준으로 변경 여부를 확인하여 같은 이미지의 크기를 매번 다시 읽지 않도록 합니다. 외부에서 이동·삭제한 파일이 조회에 반영되는 기존 계약은 유지합니다.

### 작업 탭: ComfyUI와 앱 DB 상태의 불일치

| 관련 탭 | 측정 항목 | 추가 점검 결과 |
| --- | --- | --- |
| 작업 / 공통 감시 | ComfyUI queue 읽기 | 실행 0개, 대기 0개. 최초 조회 14.7 ms |
| 작업 / 공통 감시 | 후속 DB 활성 요청 수 | 157개. 모두 측정 시점의 queue에는 없음 |
| 작업 / 공통 감시 | 위 요청의 history를 직접 조회 | `pending` 129개는 history 없음, `pending` 22개와 `running` 1개는 success 기록 있음, `cancelling` 5개는 history 없음 |
| 공통 감시 | 위 157개 history의 순차 읽기 전체 시간 | 806.8 ms. 앱 감시 전체 주기의 소요 시간은 아님 |

DB와 queue·history는 순차 조회했으므로 하나의 원자적 Snapshot은 아닙니다. 점검 중 실제 작업 상태도 바뀌었습니다. 다만 queue에도 없고 history에도 없는 `pending` 요청을 다수 확인했고, 완료 history가 있는데 앱 상태 반영이 뒤처진 요청도 확인했습니다. queue·history에서 사라진 최초 원인은 현재 로그만으로 확정하지 못했습니다.

현재 `_refresh_requests()`는 queue와 history에 모두 없는 요청이 `cancelling`일 때만 15초 후 취소로 확정합니다. `pending`·`running`이면 상태를 종료하지 않고 계속 조회합니다. 따라서 사라진 요청이 대기·실행 상태로 남고, 같은 빈 history를 반복 조회할 수 있습니다. 이 경우 재취소가 ComfyUI에서 거절되면 앱도 취소 실패로 처리합니다. **이번 점검에서 직접 취소를 실행하여 거절 응답을 확인한 것은 아닙니다.**

### 작업 탭: 전체 취소의 누락·순차 처리

- `cancel_job()`은 `pending`·`running`만 취소하며, `submitting`은 제외합니다. `_submit_requests()`에는 작업 취소를 확인하고 남은 제출을 중단하는 처리가 없습니다. 따라서 제출이 끝나기 전에 전체 취소를 누르면, 그 뒤 새 하위 요청이 계속 접수될 수 있습니다. 코드로 확인한 문제이며 이번 점검에서 별도 실제 취소 재현은 하지 않았습니다.
- 대상 요청을 하나씩 ComfyUI에 순서대로 취소하고, 각각 DB를 갱신한 뒤 전체 HTTP 응답을 반환합니다. 모든 대상 처리가 끝날 때까지 Browser에 최종 취소 접수 건수가 표시되지 않습니다.
- 로그에는 22:13:09~22:13:20 사이 취소 접수 5건, 22:13:21 무렵 작업 취소 API `200 OK`가 기록됐습니다. 사용자의 실제 조작에서 일부 취소가 접수된 근거이며, 전체 100개 취소가 완료됐다는 의미는 아닙니다. 클릭 시작 시각과 API 응답 본문의 건수는 로그에 없어 전체 소요 시간은 확정할 수 없습니다.
- 최근 큰 작업 두 개에 `stopped` 50개·34개가 기록돼 있었습니다. 코드상 앱 기동 시 남아 있던 `submitting` 요청을 이렇게 표시합니다. 로그에도 22:11:12 서버 시작이 있습니다. `stopped`는 ComfyUI 취소 완료와 다른 상태입니다. 이번 진단에서는 서버를 재시작하지 않았습니다.

### 이번 점검으로 추가된 개선 항목

1. 상태 추적에는 ID·상태·시각 등 최소 필드만 조회하고 전체 후보 Snapshot parsing을 제외합니다.
2. queue·history에서 사라진 요청을 반복해서 대기로 남기는 정책을 보완합니다. 일시적인 조회 불일치와 실제 유실을 구분하며, 사라졌다는 이유만으로 완료나 취소로 단정하면 안 됩니다.
3. 작업 단위 취소 의도를 기록하여 아직 제출하지 않은 하위 요청도 중단하고, 제출 중 ComfyUI에 접수된 요청의 취소 누락을 막습니다.
4. 취소 진행·실패 건수를 화면에 표시하고, 순차 취소의 지연을 줄이는 처리 방식을 검토합니다. 다른 작업의 queue까지 취소하는 전역 삭제는 사용하지 않습니다.

## 개선 시 유지할 동작

## 적용 및 검증 상태

- 진단 과정에서 코드·설정·DB schema를 변경하거나 서버를 재시작하지 않았습니다.
- 실제 작업과 결과물은 삭제하지 않았습니다. 삭제 흐름 검사는 Mock API에서만 수행했습니다.
- 실제 HTTP 측정에는 별도 로그인 Session을 사용했고 측정 후 로그아웃했습니다.
- 점검 전후 Git Working tree는 clean이었습니다. 이 문서 작성만 새로운 변경사항입니다.
- 향후 개선 시 느린 응답, 삭제 직후 목록 갱신, 보호 변경, 페이지 이동, 실패 재시도에 대한 회귀 검증이 필요합니다.

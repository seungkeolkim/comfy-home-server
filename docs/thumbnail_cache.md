# 결과물 썸네일 Cache

작업일: 2026-10-11. 브랜치: `codex/job-cancellation-performance`.

결과물 Preview는 같은 이미지가 다시 요청될 때도 서버에서 원본 decode·방향 보정·resize·WebP 압축을 반복했습니다. Browser의 조건부 요청은 ETag가 같을 때 304로 응답했지만, 조건 없는 재요청이나 다른 Browser에서는 변환 비용이 다시 발생했습니다.

## Cache에 남는 데이터

- 최대 384px, WebP quality 75로 압축된 `bytes`만 보관합니다.
- 원본 bytes, Pillow Image, decode된 Bitmap, 변환 Buffer는 Cache에 저장하지 않습니다. 생성 함수가 끝나면 Bitmap과 Buffer를 닫습니다.
- `config.toml`의 `[outputs].thumbnail_cache_max_entries`로 최대 개수를 지정합니다. 기본 10,000개, 1 이상의 정수이며 총 bytes 제한은 두지 않습니다.
- 조회한 항목을 LRU의 최근 사용 위치로 옮기고 개수를 넘으면 가장 오래 조회하지 않은 항목을 제거합니다.
- Cache Key는 관리 폴더 안으로 검증한 절대 경로·수정 시간(ns)·파일 크기입니다. 같은 파일을 바꾸면 새 Key로 생성합니다. 이전 버전도 LRU 개수에 포함되며 사용되지 않으면 퇴출됩니다.
- API는 Cache 조회 전 인증·관리 경로·현재 파일 존재를 확인합니다. Cache에 남은 bytes 때문에 삭제한 파일을 계속 반환하지 않습니다. 파일 수정 시간과 크기가 모두 그대로인 외부 변경은 기존 ETag와 마찬가지로 감지할 수 없습니다.
- ETag·304 계약, 영상의 원본 열기, GIF의 정지 Preview, 손상 이미지의 422·과대 이미지의 413 응답을 유지합니다.

## 생성 중의 메모리와 동시 요청

원본을 처음 변환하는 동안에는 Bitmap과 방향·색상 변환 복사본이 필요합니다. Cache Hit는 이를 다시 생성하지 않습니다. 같은 Key의 동시 Cache Miss는 하나의 `Future`를 공유하여 한 번만 변환합니다. 서로 다른 Key의 변환도 `BoundedSemaphore`로 동시에 최대 두 건으로 제한합니다. 따라서 동시에 여러 썸네일을 요청해도 모든 원본 Bitmap을 한꺼번에 펼치지 않습니다.

파일 변환과 Cache 대기는 FastAPI Worker Thread에서 수행하며 Event Loop에서 동기적으로 기다리지 않습니다. Cache 자료구조 Lock 안에서 이미지 읽기나 변환을 하지 않습니다. 이는 원본 한 장의 decode 비용 자체를 없애거나 개별 원본의 메모리를 작은 썸네일 크기로 제한하는 기능은 아닙니다.

## 기동 시 백그라운드 채우기

`[outputs].thumbnail_cache_warmup_enabled = true`이면 Lifespan에서 별도 Thread를 시작합니다. 기본값은 `false`이며 개발 중 잦은 재기동 때 원본 읽기·CPU 변환을 반복하지 않도록 바로 조회한 이미지만 채웁니다.

백그라운드 Thread는 전체 관리 폴더의 파일 정보만 탐색하고, 가장 최근 이미지 후보를 최대 Cache 개수까지만 선택합니다. 이후 한 장씩 생성하고 각 변환 사이에 50ms 대기합니다. 후보 정보의 메모리는 `heapq.nlargest`를 사용해 최대 선택 개수에 맞춰 유지합니다. 손상되거나 삭제된 파일은 건너뛰므로 실제 채워진 개수는 후보 수보다 적을 수 있습니다.

백그라운드가 넣은 항목은 사용자가 조회한 항목보다 먼저 퇴출되도록 LRU의 오래된 위치에 삽입합니다. Cache가 차면 채우기를 중단하며 사용자가 최근 조회한 항목을 퇴출하지 않습니다. 실제 조회와 백그라운드가 같은 Key를 처리하면 하나의 변환 결과를 공유합니다. 전체 동시 변환 제한 두 건 안에서 백그라운드는 한 건씩만 실행합니다.

각 파일의 원본을 읽기 직전에 경로·현재 수정 시간·크기를 다시 확인하고, 현재 버전이 Cache에 있으면 해당 파일을 즉시 건너뜁니다. 목록 확인 이후 파일이 바뀌고 사용자가 새 버전의 썸네일을 채웠어도 재읽지 않습니다. 이 확인 직후 사용자 요청이 들어오는 경합은 `get_or_create()`의 Lock 안에서 Cache·진행 중 Future를 다시 확인하여 하나의 생성 결과를 공유합니다. 완료 로그의 `reused`는 원본 읽기 전에 Cache Hit로 건너뛴 개수입니다.

서버 기동은 파일 탐색과 이미지 변환을 기다리지 않습니다. 종료 시 중단 신호를 보낸 뒤 실행 중인 한 건의 변환이 끝나기를 Worker에서 기다리고 Thread를 정리합니다. 시작·완료·건너뛴 개수·중단 여부는 앱 로그에 남깁니다. 썸네일 파일을 SSD에 쓰지 않으며, 재기동마다 원본 읽기·변환 비용은 다시 발생합니다. OS 파일 Cache의 재사용 정도에 따라 실제 SSD 읽기량은 달라집니다.

## 범위

이번 변경은 썸네일 Cache와 백그라운드 채우기에 한정합니다. 결과물 목록 API가 페이지 조회마다 전체 폴더를 탐색·정렬하는 구조와 출력 경로의 작업 이력 연결 조회는 유지합니다. 해당 비용은 별도의 목록 Index 개선 대상입니다. DB Schema·작업 상태·생성물·삭제 보호·UI는 변경하지 않습니다.

## 검증

- 압축 WebP bytes만 보관하는지, 결과 크기가 384px 이내인지 확인합니다.
- LRU 퇴출, 현재 파일 변경 감지, 실패 후 재생성, 같은 파일 동시 요청의 단일 생성, 다른 파일의 최대 두 건 변환을 검사합니다.
- 최신 후보 선택·최대 개수·Foreground 보존·손상 파일 건너뛰기·종료 시 중단을 검사합니다.
- 옵션 On/Off와 느린 백그라운드 생성 중 Session·100건 취소 응답을 검사합니다.
- 실제 Preview API의 재요청 Cache Hit·ETag·인증·파일 변경·이동·삭제·413 처리를 검사합니다.
- 기존 설정 파일의 기본값과 잘못된 타입·범위 거부를 검사합니다.

Python 전체 테스트 **134개 통과**, `git diff --check` 통과. 아래는 Cache 최초 적용 시 실제 서버의 기존 최신 이미지 12개를 조건부 헤더 없이 연속 조회한 결과입니다. 파일별 직전 재검사 보완 전의 측정이며, Container 내부 HTTP 기준입니다. Browser·모바일·외부 네트워크 시간은 포함하지 않습니다.

전체 백그라운드 채우기 시간에는 이미지 사이의 50ms 대기도 포함됩니다. 서버의 기본 설정은 Off로 유지하고 검증용 별도 Cache에서 수행했습니다. Cache Hit에서도 현재 파일 경로·존재·속성 검사는 유지하므로 Windows bind mount의 파일 정보 확인 비용까지 사라지지는 않습니다. 이 결과는 해당 파일 집합과 실행 환경의 측정이며 모든 이미지에서 같은 속도나 압축 용량을 보장하지 않습니다.

읽기 전용 실제 검증 전후 작업 70개·요청 612개의 DB 개수가 같음을 확인했습니다. 생성·삭제 요청과 썸네일 파일 쓰기는 수행하지 않았습니다. 최초 검증 때는 기동 시 채우기를 Off로 적용했습니다. 이후 사용자 요청에 따라 `config.toml`의 기동 시 채우기를 On으로 변경하고 Compose 서버를 재기동했습니다. LRU 최대 개수는 10,000입니다. 설정을 생략한 경우의 기본값은 Off이며, 원본 읽기와 변환이 한 번씩 필요하므로 반복 재기동 비용을 피하려면 Off로 변경할 수 있습니다.

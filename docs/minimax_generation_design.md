# MiniMax 작업 생성 UI 검토

작성일: 2026-10-19

상태: **기본 범위를 구현했습니다.** 초기 검토사항은 아래에 보존하고, 확정한 동작과 검증을 6장에 기록합니다. 설계 문서는 구현 전에 `c390d65`로 커밋했습니다.

작업 브랜치: `feat/minimax-generation-modes`

## 1. 사용자 요청 범위

- 이미지와 평문 Prompt만 입력하여 F2VA, L2VA, FL2VA 작업을 생성합니다.
- Ref video와 Ref audio 입력은 제공하지 않습니다. Reference 입력 제외와 생성 영상의 Audio 출력 여부는 별개입니다.
- 영상 생성 방식과 처리 대상을 각각 선택합니다.
- 처리 대상은 이미지 한 장으로 영상 한 개를 만드는 단건 작업, 폴더의 이미지마다 독립된 영상을 만드는 다중 작업으로 구분합니다.
- 서버 결과물 루트 안에서 기존 탐색기를 확장하여 이미지 또는 폴더를 선택하는 방향입니다. [폴더 탐색기 설계](output_folder_picker_design.md)의 경로 경계를 재사용합니다.

## 2. 추가 요청: 모든 모드에서 이미지 입력 영역 하나 사용

이번 FL2VA는 서로 다른 첫·마지막 이미지를 받는 일반적인 두 이미지 입력 방식이 아닙니다. **이미지 한 장을 양쪽 endpoint에 동일하게 넣습니다.**

| 생성 방식 | 요청 한 건의 입력 이미지 | 첫 Frame | 마지막 Frame |
|---|---|---|---|
| F2VA · 이 이미지로 시작 | 한 장 | 선택 이미지 | 지정하지 않음 |
| L2VA · 이 이미지로 끝 | 한 장 | 지정하지 않음 | 선택 이미지 |
| FL2VA · 같은 이미지로 시작·끝 | 한 장 | 선택 이미지 | 동일한 선택 이미지 |

- 첫 이미지/마지막 이미지용 입력창을 따로 두지 않고, 세 모드 모두 공통 이미지 입력 영역 하나를 사용합니다.
- 현재 화면의 두 파일 선택 control은 첫·마지막 Frame용이 아니라 `minimax-images`와 `minimax-directory`, 즉 파일 선택과 폴더 선택용입니다. 개편 시 이 선택도 공통 입력 영역 안에서 단건/폴더 대상에 따라 전환하는 방향으로 검토합니다.
- 단건에서는 이미지 하나를 선택하고 Preview를 표시합니다. 폴더에서는 선택 폴더와 대상 이미지 목록·개수를 표시합니다.
- 폴더 작업의 FL2VA도 각 이미지로 독립된 영상을 만듭니다. 서로 다른 이미지를 첫·마지막 Frame으로 짝짓거나 영상 하나로 이어 붙이지 않습니다.
- UI에는 `같은 이미지로 시작·끝`을 표시합니다. 자연스러운 Loop를 보장하는 의미로 표시하지 않습니다.

## 3. 추가 검토: 첫 이미지 해상도로 공통 해상도 자동 입력

사용자 제안은 **선택한 첫 이미지의 너비·높이를 영상 해상도 기본값으로 자동 입력**하는 것입니다. 폴더 내 이미지는 보통 같은 해상도지만, 서로 다른 해상도가 섞인 경우도 고려합니다.

### 기본 동작안

- 단건은 선택한 이미지의 해상도로 너비·높이를 채웁니다.
- 폴더는 제출 대상 이미지 목록의 첫 이미지 해상도로 너비·높이를 채웁니다.
- 폴더 작업에는 자동 입력한 공통 해상도 하나를 적용합니다. 이미지마다 다른 출력 해상도로 자동 전환하는 방식은 이번 기본안에 포함하지 않습니다.
- 화면에 기준 이미지 이름과 해상도를 함께 표시하여 자동값의 출처를 확인할 수 있게 합니다.
- 기준은 입력 이미지의 실제 해상도입니다. Catalog에 있는 생성 요청 해상도가 실제 파일 해상도와 같다고 가정하지 않습니다. 크기 확인은 Thumbnail 확대가 아닌 이미지 header 등의 실제 입력 정보로 처리하는 방향을 검토합니다.

### 구현 전에 구체화할 사항

1. **첫 이미지의 순서:** FS 열거 순서나 결과물 페이지의 첫 항목에 의존하지 않습니다. 대상 목록의 정렬 규칙을 고정하고, 화면에 표시한 첫 제출 대상과 기준 이미지를 일치시키는 방안을 검토합니다.
2. **혼합 해상도:** 첫 이미지의 공통 해상도를 유지하면서 나머지 이미지의 Resize 방식을 정해야 합니다. 특히 종횡비가 다를 때 Crop·Pad·Stretch 중 어떤 정책을 쓸지 별도 결정이 필요합니다. 혼합 여부를 표시하는 방법과 그 확인 비용도 함께 검토합니다.
3. **수동 수정:** 자동 입력 뒤 너비·높이를 직접 수정할 수 있도록 하는 방안을 검토합니다. 입력 대상을 바꾸거나 첫 이미지를 체크 해제했을 때 수동값을 유지할지, 자동값을 다시 적용할지 명시해야 합니다.
4. **지원 해상도 정렬:** 현재 `prepare_minimax()`는 기본적으로 너비·높이를 32 단위로 올림합니다. 입력 원본 해상도와 실제 제출 해상도가 달라질 수 있으므로, 설치된 Workflow의 제약을 확인하고 보정값을 화면에 표시하는 방안을 검토합니다.
5. **확인 실패와 큰 원본:** 첫 이미지의 해상도를 읽을 수 없는 경우와 Workflow가 처리할 수 없는 큰 해상도에 대한 안내·직접 입력 경로를 정합니다. 다른 값으로 조용히 대체하지 않습니다.
6. **이력:** 기준 이미지, 자동으로 읽은 크기, 사용자가 최종 선택한 크기와 실제 제출 크기를 어떻게 기록할지 검토합니다.

## 4. 앞선 아이디어에서 이어서 검토할 사항

아래는 권장안이며 아직 모두 확정한 사항은 아닙니다.

- UI는 생성 방식 → 처리 대상 → 공통 이미지 입력 → Prompt → LoRA → 영상 옵션 → 제출 요약으로 구성합니다.
- Prompt는 평문 그대로 유지하며, 폴더 작업의 모든 이미지에 같은 Prompt를 적용합니다.
- 폴더는 우선 직하위 이미지만 표시하고 제출 전 대상 이미지를 체크 해제할 수 있도록 합니다. 하위 폴더 포함 여부는 별도 결정합니다.
- 제출 전 `FL2VA · 이미지 24장 → 영상 24개 · 공통 해상도 · 각 영상 길이`처럼 실행 규모를 표시합니다.
- 제출 시 대상 목록을 확정하고 입력을 임시 복사하는 Snapshot 방식을 검토합니다. 대기 중 원본 이동·삭제로부터 입력을 분리하고, 원본 ID와 선택 당시 경로를 이력에 남깁니다.
- 현재 Batch 상한 100장을 고려하여 초과 시 조용히 일부만 제출하지 않도록 합니다.
- 상위 작업 하나 아래 이미지별 독립 요청을 생성하는 기존 구조를 재사용합니다. 실패한 요청만 재시도하는 UI와 처리 방식은 구현 범위를 정할 때 별도 확인합니다.
- Workflow는 공통 API/UI JSON 템플릿 하나를 복제하고 모드별 endpoint 구성을 채우는 방식을 우선 검토합니다. 전체 Graph를 매번 새로 생성하거나 모드별 공통 설정을 세 벌에 중복 관리하는 부담을 줄입니다.
- Director의 실행 모드, Timeline, Builder state, 저장 Metadata를 같은 설정에서 함께 생성합니다. F2VA 화면 표기와 설치 Node의 실제 모드명 매핑도 검증합니다.

## 5. 변경 범위와 검증

초기 문서 작성 단계에서는 사용자 추가 요청만 기록했습니다. 현재 구현 내용은 다음 장을 기준으로 확인합니다.

## 6. 구현 기록과 결정사항

- 세 모드에서 공통 이미지 입력 영역 하나를 사용합니다. 초기값은 기존 동작인 FL2VA입니다. Ref video/audio 선택은 추가하지 않았습니다.
- 설치된 `ComfyUI-DaSiWa-Nodes`의 Director 코드에서 `I2VA`, `L2VA`, `FL2VA` 실행 모드와 endpoint slot을 확인했습니다. 화면의 F2VA는 내부 I2VA/slot 0, L2VA는 slot 1, FL2VA는 같은 업로드 이미지의 slot 0·1로 매핑합니다.
- API/UI JSON 템플릿은 기존 한 벌을 재사용합니다. 복제본의 Director mode, Timeline, Builder state와 Metadata를 함께 갱신하고, 이전 Reference 및 continuity 상태를 제거합니다.
- 공용 탐색기에 이미지 한 장 선택과 폴더 이미지 선택 모드를 추가했습니다. 입력 선택에서는 새 폴더 생성 UI를 숨깁니다. 폴더는 직하위 이미지를 파일명 `casefold` → 원래 이름 → 경로순으로 정렬하며, 서버가 반환한 순서를 화면·해상도 기준·제출 순서에 동일하게 적용합니다.
- 후보 조회는 Catalog를 사용하고 일반 결과물 페이지네이션과 무관하게 전체 직하위 이미지를 반환합니다. 후보 조회로 FS 전체 Sync를 수행하지 않습니다. 삭제된 이미지와 영상은 제외하며 삭제 보호된 이미지는 읽기 입력으로 사용할 수 있습니다.
- 현재 폴더의 후보를 선택·해제하고 최대 100장만 확정할 수 있습니다. 확정한 입력의 실제 크기는 별도 API에서 최대 100장에 한해 확인합니다. 생성 요청 해상도나 Thumbnail 크기는 사용하지 않고 실제 header와 EXIF 방향을 읽습니다.
- 자동 해상도는 첫 선택 이미지의 너비·높이입니다. 공통 해상도 하나를 모든 요청에 적용하며 다른 크기가 섞이면 표시합니다. 자동 모드에서 첫 이미지를 해제하면 다음 선택 이미지의 크기를 적용합니다.
- 너비·높이 직접 입력은 수동 모드로 전환합니다. 이후 선택 대상을 바꾸거나 체크 해제해도 수동값을 유지하며, `첫 이미지 해상도 다시 적용`을 누르면 자동 모드로 돌아갑니다. 이력 복원은 기존 해상도를 보존하고 입력 이미지는 다시 선택하도록 합니다.
- 기존 32 단위 올림 정책을 유지합니다. 화면에 원본 크기와 실제 제출 크기를 함께 표시하며, 너비·높이는 16~8192 정수 범위를 검사합니다. 큰 원본을 조용히 축소하지 않고 직접 입력을 안내합니다.
- Resize는 EXIF 방향 보정 → RGB/검은 배경 합성 → 비율 유지 Fit/검은 Pad입니다. Snapshot 원본은 보존한 채 공통 Canvas의 PNG를 따로 만듭니다. Director에서는 준비한 Canvas를 다시 Resize하지 않도록 Input scaling을 Off로 지정합니다. Metadata의 해상도 선택도 Fixed pixels로 맞춥니다.
- 접수 시 모든 선택 ID의 현재 경로·삭제 여부·폴더 소속을 확인하고 서버 runtime에 원본 Snapshot을 복사합니다. 이미지 한 장당 기존 50 MB 제한을 적용하며, 중간 복사·해상도 확인·DB 기록 실패 시 이번에 만든 임시 파일을 전부 회수합니다. ComfyUI 제출 후 기존 Batch 정리 경로가 원본 Snapshot과 준비 PNG를 모두 제거합니다.
- DB schema는 변경하지 않습니다. 작업 공통 입력에는 생성 방식·대상 범위·기준 이미지·사용자 해상도를 저장하고, 요청별 result에는 원본 ID·경로·실제 크기와 확정 제출 해상도를 보관합니다. 상위 카드에는 모드/입력 범위를, 하위 요청에는 입력 출처를 표시합니다.
- 후보/해상도 확인은 `/api/outputs/input-images`, `/api/outputs/input-images/inspect`를 사용합니다. `/api/batches`는 `output_ids`, `input_scope`, `input_directory`를 받습니다. 기존 업로드 API 입력은 호환성을 유지하지만 새 UI는 서버 탐색기를 사용합니다.
- 기존 상위 작업/이미지별 독립 요청 구조를 재사용합니다. 실패 요청만 다시 제출하는 전용 UI는 추가하지 않았으며 후속 범위로 유지합니다.

검증은 임시 파일·Fake ComfyUI client·Desktop/Mobile Mock API Browser로 수행합니다. 실제 GPU 영상 생성은 수행하지 않습니다. 운영 결과물을 이동하거나 삭제하지 않습니다.

검증 결과:

- Python 전체: `228 passed, 1 skipped`.
- Desktop/Mobile MiniMax 생성 UI: 세 모드, 단건/폴더, 자동/수동 해상도, 혼합 크기, 100장 상한, 취소·실패·이전 응답 무효화를 통과했습니다.
- Backend: 실제 EXIF 크기, 삭제 보호 이미지의 입력 사용, 모드별 API/UI Metadata 일치, 원본 삭제 후 Snapshot 사용, 접수 실패/용량 초과 정리, 임시 파일명 충돌 보존, symlink/junction 경계를 통과했습니다.
- 기존 Browser 회귀: 작업 복원, 결과물 이동·삭제/공용 탐색기, 탭/History, LoRA·작업·태그 흐름을 통과했습니다. LoRA Browser fixture의 이전 24건 기대값은 현재 64건 페이지 기준으로 맞췄습니다.
- 실행 중인 Docker 서비스에서 새 API와 Batch 입력 schema 반영, `healthy` 및 Session HTTP 200을 확인했습니다.
